## §10, with its central mechanism inverted

**[`78d1885`](https://github.com/Thibico/thibi-transcribe/commit/78d1885) — Make a cancel reach
the step that is already running**

The rule §10 opens with is that *a cancel that only stops the next step is not a cancel*. The
expensive work is the step already in flight — a chunk mid-request, a forty-minute diarization —
and reaching it is the whole problem. The plan solves it with a `LISTEN run_cancel` channel that
every worker subscribes to.

The notify is sent, because the UI will want it and because adding a subscriber later should be
a subscriber and not also a producer. But nothing subscribes to it, and the mechanism that
actually reaches a running handler is the heartbeat's existing statement with one extra join:
`returning (r.cancel_requested_at is not null)`.

**The reason is failure mode, not latency.** A `LISTEN` needs a dedicated non-pooled client held
open for the life of the process, and when it dies nothing throws — cancellation silently stops
working until somebody notices a run that will not die. This phase has an open investigation
into exactly that shape: a poll chain that went quiet for two hours with nothing logged. Putting
a *guarantee* behind a second subsystem with the same failure mode would have been repeating the
mistake while still reading the report on it.

The heartbeat is the opposite shape. It already runs every fifteen seconds for every running
step, already round-trips to Postgres, already aborts the handler when it dislikes what it
finds. The state lives in the row rather than in a message that was or was not delivered, so a
missed check is retried fifteen seconds later, forever. The price is up to fifteen seconds of
latency — and **a cancel that arrives late is a delay where a cancel that never arrives is a
bug**. The listener is still worth building, as an accelerator over that guarantee rather than
as the guarantee. Amendment 102.

Migration `0005` adds `runs.cancel_requested_by`, which §10 has been writing since phase 1
without the column existing. `text` rather than a `users` reference, on two counts: the CLI
cancels with nobody signed in, and a run's audit trail has to outlive the account that triggered
it — a cascade would delete precisely the record someone is asking about.

`requestCancel` moved out of `batch-persist.ts`, where a second and thinner version had been
living: it wrote the timestamp and nothing else — no requester, no event, no notify. Two
functions of the same name doing different amounts of the same job is the drift this repo has
already paid for twice, so that one is now a re-export of the real one. It is idempotent by
predicate rather than by check, returns whether it actually acted, and deliberately does not
reconcile: it is called from places with no doorbell on the context, so the caller reconciles
when it can and the thirty-second tick does it otherwise.

## A busy sidecar is not a broken one

Running the full suite while a worker was mid-diarization turned `pyannote.contract.test.ts`
red. Its `beforeAll` submits a task, my own run held the sidecar's only slot, and
`DiarizerBusyError` escaped as a suite failure.

That is wrong twice over: nothing is broken, and the message names a busy queue rather than a
bug. "Somebody else is using the machine" belongs with "the sidecar is not running", which this
file already skips for. Its readiness probe now checks `slots.busy` alongside the model state.

It only became reachable this week, which is why it survived until now: before the `diarize`
handler existed, nothing in the system but that test ever submitted a task, so the slot was
never contended.

## The stall hunt: nothing caught, and a number worth having

A 16 m 37 s recording was put through deliberately to try to reproduce the two-hour poll stall,
with the new overdue-poll warning armed. It finished clean: **95 polls at a steady sixteen-second
cadence**, no `overdue` warning, no recovery tick repairing anything — against the 23 polls at
which the original broke. Both long-async shapes ran in the same run, batch ASR finishing in 5
polls and 390 s. All eleven steps `done`, 295 turns attributed across 35 segments, two speakers,
$0.04985.

**That is not a clean bill of health.** The stall has been seen once and not reproduced, and a
hunt that catches nothing narrows nothing by itself. What it does rule out is a defect that fires
reliably on every long poll chain — whatever this was, it is intermittent.

What the run *did* settle is a number the project has been quoting badly. Diarization on this box
runs at **0.669× realtime** — 16 m 37 s of audio in about 25 minutes of CPU. That is the first
diarization figure measured on a clip long enough to clear amendment 56, and it **confirms** S6's
0.6× rather than contradicting it: pyannote 4.0.7 is not meaningfully slower than the 3.1 S6
measured. Yesterday's worry that it had become four times slower came from two probes that were
too short and, in one case, taken while a test suite competed for the machine. A one-hour
interview is about an hour and a half of diarization, which is what the GPU-tier question
(open question 3) actually needs to be answered against.

With the slot free again, the pyannote contract suite was re-run and all six passed — so the six
skipped in the commit above are now accounted for rather than left as a green-looking gap.
