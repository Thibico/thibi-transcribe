# Phase 1 — the engine

Seven commits taking the repo from a language registry to
`thibi transcribe interview.m4a --lang my` producing a real transcript with word timings
and per-word confidence, persisted to Postgres and MinIO.

Executed against
[`plans/phase-01-engine-core.md`](../plans/phase-01-engine-core.md). The phase sits before
anything user-facing because it is the narrowest path that touches every seam the rest of
the build hangs off: Phase 2 adds a mode to the provider, Phase 3 a stage consuming the
same normalized derivative, Phase 4 more providers behind the same interface, Phase 9 the
`run_steps` state machine, Phase 11 a UI over the same JSON.

**Two of the plan's own "decide on day one" risks were settled first.** `await using`
disposes in reverse order and runs on throw under Node 22.18 with our tsconfig (risk 7).

## `bc90d42` — core primitives, the ObjectStore port, the database schema

Three of the six packages.

**`packages/core`** gains the wire-neutral transcript types, timecode, the no-words
interpolation fallback and `resolveLayer`. Two decisions worth recording:

- `interpolateWords` takes a minimal structural `SegmentationRules` rather than the
  `ResolvedLanguage` the plan specified. `core` may depend on nothing — that is the ESLint
  layer rule from Phase 0 — and it must stay importable from a React client component. The
  caller passes the two fields that matter. A small deviation, and the alternative was
  either breaking the layer rule or duplicating the function.
- `formatTimestamp` works in integer milliseconds and rounds exactly once, killing
  [overview amendment 3](../plans/00-overview.md) at the root. The old `lib/export.ts:15-22`
  turned 59.9996 s into `00:00:59,1000` — a four-digit millisecond field and malformed SRT —
  because the rounding never carried into the seconds. The regression test asserts that
  input and the full 23:59:59.9996 cascade.

**`packages/storage`** is one port, three adapters, one `describe.each` contract suite. That
is what makes `STORAGE_DRIVER=fs` — the overview's Risk-4 cut list — a supported
configuration rather than a degraded one, and it lets everything above this layer test
without a container. `toTempFile` hardlinks when the store is fs-backed on the same device,
and its directory is gone after both a normal return and a throw, which is the whole reason
for `await using` over a `finally`.

**`packages/db`** is the schema, our own migration runner and `copyWords`. The generated
`0000_init.sql` has 11 tables with the partial unique indexes and CHECK constraints intact.
The load-bearing details: `segment_texts.target_lang` is NOT NULL defaulting to `''`,
because a partial unique index over a NULLable column enforces nothing (`NULL <> NULL`) and
a test that only inserts translations would never notice; `words.id` is a bigint identity
rather than a uuid, because 10M rows at 1,000 audio-hours makes a random primary key double
the index and destroy COPY's insert locality; and the migration runner is ours rather than
drizzle-kit's because [Phase 15](../plans/phase-15-deployment.md) runs it as a compose
one-shot with no dev tooling in the image.

## `9623281` and `94417cd` — engine core, audio stages, seam merge, Google provider

82 tests. The seam merge is the phase's real algorithm.

Chunk *k+1* is extracted 1200 ms before chunk *k* ends, so its transcript repeats the tail
of chunk *k* — and spike S3 measured that hard cuts lose 2–3 words at every seam, 2.1% of
all words at 30 minutes and 3.4% at 2 hours. LCS over a time-bounded window de-duplicates
it. Below a Dice score of 0.5 it hard-cuts at the overlap midpoint and flags the seam,
because a duplicated sentence reads as the speaker repeating themselves, which is worse for
a reader than a missing one. Unspaced scripts align on graphemes, since provider "words" in
Burmese are syllable fragments that do not tokenise the same way twice. An empty overlap
scores 1 by convention rather than NaN — a low score there would flag every pause in a
recording.

Three things measured while building, each of which changed the code:

- **A lead at or above the chunk maximum** drove the planning window to nothing and produced
  thousands of one-millisecond chunks. `--overlap-ms` is user input, so it clamps to half
  the maximum rather than failing obscurely.
- **Zawgyi conversion is byte-identical per word and whole-string**, because the reordering
  it does never crosses a word boundary. That is the property per-word conversion depends
  on, so it is asserted rather than assumed. My first attempt asserted the conversion was
  not length-preserving — which is not true for real Burmese, and was the wrong
  justification anyway. The right one: converting segment text in place leaves the word
  array in Zawgyi and the two disagreeing, and the alignment cannot be recovered by
  re-splitting because the transform reorders within syllables.
- **The token cache renews at 44 minutes, not 45** — a 45-minute recorded lifetime with a
  60-second guard. The guard is what stops a request starting just under the wire from being
  the one that fails.

`google/parse.ts` is where the word array becomes the *output* rather than a source of
bounds; `google.ts:207-221` read the first and last offsets and threw the array away.
`google/errors.ts` ports `toError` with `:139-141` deleted — the hint that appended "check
the region: Chirp 2 and Burmese only overlap in asia-southeast1 and europe-west4" to every
INVALID_ARGUMENT naming a model or language. It is a false statement that sent operators to
re-check a setting that was never the problem, and a test now asserts no message this module
produces names a region.

`capabilities.ts` carries the S1 and S2 verdicts as literals with their dates, so
`adaptation: 'none'` traces to [the spike](../spikes/RESULTS.md) that found an irrelevant
phrase set corrupting five occurrences of a word the baseline got right.

The second commit is a correction: lint caught an unused `minScore` in the no-words seam
branch, which was a real gap rather than a style nit. Thinking it through, the score
*cannot* change the decision at segment granularity — the overlap region contains audio we
extracted twice, so something was said twice whether or not the two transcriptions of it
agree. The score is now documented as informational, and what it would take to act on it is
written down.

## `d5ec420` — the pipeline and the CLI

`thibi transcribe` runs the whole slice. Verified on a real 100-second Burmese file: 2
chunks, 197 words with full timings and per-word confidence, 13 seconds, $0.027.

**Running it on real audio found a bug no unit test had.** The seam windowed prev-side words
by `endMs`, so a 760 ms word that *began* before the overlap was included — audio chunk
*k+1* never received and therefore can never align. It dropped the score from 0.86 to 0.43
and forced a hard cut on a perfect seam. The plan's own pseudocode says `startMs`; I had
deviated. Fixed, and the file now scores 1.0.

One unit test failed on the fix, and the fixture was what was wrong: it gave chunk *k* a
word extending past its own end, which is audio that chunk does not have. Corrected to
realistic geometry, and the real-file case became its own named regression test.

**The measured benefit of the overlap, on that file:** 197 words with the merge against 196
with `--overlap-ms 0`, both reading identically at the seam. The overlap recovered a word
the hard cut would have lost and the merge removed the duplicate it introduced — exactly
what spike S3's 2–3-words-per-seam measurement predicted.

`apps/cli/src/context.ts` is the only file that reads the environment, and its key list is
exhaustive and reviewed. `--no-db` is a memory store rather than a special case threaded
through the pipeline, which is what keeps persistence a stage. Exit 4 prints the transcript.

Both CI greps now strip comment lines before matching. The rules are worth explaining where
they are enforced, and a check that forbids naming the thing it forbids would delete its own
documentation — here, the record of which false region claim was removed and why.

## `6d10a19` — persist, the normalize cache, and live verification

Docker came up, and the suites that had been skipping found the gaps they exist to find.

- **The constraint assertions were reading the wrong object.** Drizzle wraps the driver
  error in a `DrizzleQueryError`, so the SQLSTATE lives on `.cause`. The helper now asserts
  the constraint *name* as well as the code, which is stronger: `23505` only says some
  unique index fired, and these tests exist to prove the particular partial index — the one
  whose `WHERE` clause is easy to get wrong — is the one that did.
- **The S3 unsafe-key case failed on the test's own scaffolding.** The namespacing proxy was
  sanitising the very inputs under test: prefixing `/absolute.txt` makes it valid and the
  adapter never gets to reject it.
- **The normalize cache was specified and not wired.** `transcribe` called `runNormalize`
  unconditionally, so the DoD line about a second run logging `normalize: cached` could not
  have passed. `ensureNormalized` now does the lookup and handles losing the
  concurrent-insert race by deleting its own blob and using the winner's — nothing else
  would ever reference the loser's to clean it up.

Verified end to end against Postgres 17 and MinIO on a real 100-second Burmese file: the
JSON word count equals `select count(*) from words` (197 = 197); no confidence written as
0; one `(verbatim,'',asr)` row per segment; `run_chunks` carrying their `overlap_lead_ms`;
raw provider responses archived; and a second run logging `ingest: asset already stored`
then `normalize: cached`, leaving exactly one asset row, one derivative row and two runs —
because runs are append-only.

CI gained Postgres and MinIO service containers plus an assertion that the db suite did not
skip. A suite that silently skips is worse than one that is absent.

# Phase 2 — `batchRecognize` and GCS staging

Four commits, executed against
[`plans/phase-02-batch-recognize.md`](../plans/phase-02-batch-recognize.md). At the end of
them `thibi transcribe long.flac --lang my --mode batch` stages a normalized FLAC into
Google Cloud Storage, persists the operation name before anything can poll it, reads the
transcript back out, archives it and sweeps the bucket — and `kill -9` mid-run costs
nothing but the time already spent.

**The phase very nearly should not have been built.** Spike S3 had already removed latency
as a reason to use `batchRecognize`: it runs at a flat 5.9× realtime and chunked parallel
sync beats it 3.6–7× at every size. That left cost as its only justification, and the cost
figure was the one number nobody had checked. `spikes/RESULTS.md` said so in as many words —
*"confirm against the actual bill before writing the routing rule into code"*. So the
afternoon began by checking it rather than by writing code.

## `79e215f` — measure the premises, then correct the plan

Two new spikes, both committed as runnable instruments, because a number nobody can
re-measure is a number that gets argued about instead.

**S5 — is batch actually cheaper?** The Cloud Billing Catalog answers this without waiting
for an invoice: `Cloud Speech-to-Text Recognition` at **$0.016/min** against
`Cloud Speech-to-Text Dynamic Batch Recognition` at **$0.003/min**. **5.33×.** The premise
holds and the phase is worth building. Two things the catalog knew that the documentation
had not said:

- Recognition is *tiered* — $0.010/min above 500k minutes a month — while Dynamic Batch is
  flat. So the 5.33× is a property of the tier and not a constant. That is the argument for
  `rates` being a table an admin can correct rather than a literal in code.
- There is a **`(Logged)` SKU at 25% off both paths**, and it buys the discount by letting
  Google retain the audio to train on. For a newsroom transcribing confidential sources
  that is a disclosure, not a saving. It is not seeded, no code sets the flag, and if it is
  ever offered it will be an explicit choice with that sentence printed next to it.

**S4 — can the credentials actually validate a staging bucket?** This one found a defect in
the plan before a line of it was implemented. The service account held
`roles/storage.objectAdmin` — the obvious least-privilege grant for a staging bucket. It
could write (200) and delete (204), and it got a **403 on `storage.buckets.get`**. It could
not read the bucket's own region or its lifecycle rule. Phase 2 refuses to stage into a
bucket whose retention it cannot verify, so as written it would have refused a correctly
configured bucket on its first check.

The plan's remedy was `roles/storage.admin`. The narrow fix is
`roles/storage.legacyBucketReader`, which adds `storage.buckets.get` and
`storage.objects.list` and nothing else — telling a newsroom to grant full bucket
administration in order to read one metadata field is advice that gets pasted once and then
lives in their IAM policy forever. After the narrow grant all four checks pass.

Two smaller findings from the same run. GCS returns `location` **upper-cased**
(`ASIA-SOUTHEAST1`), so the case fold in the region comparison is load-bearing rather than
defensive. And the **Speech service agent needed nothing at all**: the plan called it the
second-most-common first-run failure, and it is absent from the bucket's IAM policy while
batch works perfectly, because enabling the Speech API creates a project-level
`roles/speech.serviceAgent` binding that already covers every bucket in that project. That
is why S3 worked. The hazard is real only for a bucket in a *different* project, and the
error hint now says so.

### The plan document was the bigger problem

Overview amendment 2 recorded on 2026-08-09 that there is no duration threshold and that
batch is an opt-in cost choice — and it was **never applied to the phase document**, which
still routed files over 900 seconds to batch and still justified the number with queue
latency the measurement had disproved. A design record that asserts what its own
measurements contradict is worse than no record, because someone will implement it.

Corrected inline, and with it went `batchMinMs`, the `asr_batch_min_seconds` setting,
`thibi bench route` (a tool whose only purpose was tuning a threshold that should not
exist) and the `warning.no_staging` event (nagging, now that the non-staging path is the
faster one). `--mode batch` without a bucket became a hard error rather than a silent
downgrade to a path costing 5.3× more than the one the user asked for.

Also corrected: the phase listed `run_steps` and `run_events` as prerequisites and they do
not exist — Phase 1 deferred the step state machine to Phase 9. The ordering invariant does
not need them, so the phase does not drag them forward for one row.

## `d271243` — the staging port, the batch provider, the routing

`staging/` is a new port with a GCS adapter, an in-memory fake, a lifecycle assertion and a
settings-time validator. It is deliberately not a second `ObjectStore`: ours holds a
newsroom's assets for as long as they want them, whereas staging is a **wire format** that
exists only because Google needs a `gs://` URI it can reach. Nothing outside `staging/gcs.ts`
knows what GCS is, which is what keeps the provider testable against recorded fixtures.

**A recorded deviation:** the adapter talks to the JSON API over `fetch` rather than
`@google-cloud/storage`, which the plan specified. Phase 1 already established `fetch` plus
`google-auth-library` for Speech, with a token cache that coalesces per credential; the
client library would build its own auth client from the same service-account JSON and give
one credential two token lifetimes, two retry policies and two ways to fail. Six
single-request operations did not justify that. The cost is no resumable upload, which does
not matter at the ~23 MB a normalized 20-minute FLAC weighs.

`planMode` is where S3's measurement finally reaches the code. Batch is now reachable
**only** through `force` — nothing about a file's properties selects it, because nothing
about a file's properties makes it the better choice. The trade is cost against latency and
only a human knows which one a given job wants. The `sync_chunked` reason names batch
without recommending it, so an operator can tell another mode exists and that not choosing
it was deliberate.

The ordering the phase exists for: `mode='batch'` and `staging_prefix` are written **before
the upload**, and the operation name plus the whole `BatchOp` land in one statement before
the first poll. Writing `mode` early was not in the plan and is what makes an interrupted
run findable at all — a run that dies between the upload and the submit would otherwise be
indistinguishable from a sync run, and nothing would ever go looking for its orphaned audio
or its orphaned operation.

`rates` and `usage_records` arrive here rather than in Phase 14 because this phase's entire
justification is a price difference, and a cost argument with no ledger behind it is a
claim.

### Two defects found by running the command, not by reading it

A **404 on bucket metadata was being reported as a permission problem**. Pointing
`settings set … --check` at a made-up bucket name answered a typo with "grant
`roles/storage.legacyBucketReader`" — precisely the class of mistake this codebase deleted
from the old app's region hint, reintroduced somewhere new and invisible until the command
was actually run against a wrong name. `BucketNotFound` is now distinct from
`BucketMetadataDenied`, carries no IAM advice, and is the one validation failure that
refuses to save the value: every other failure is a grant or a rule an admin fixes against a
bucket that exists, and this one is a name to correct.

## `e86aca0` — verified against Google, and the 192 kHz bug that fell out

A 20-minute Burmese file end to end, twice, plus the crash test.

| | measured 2026-08-10 |
|---|---|
| latency | **258 s for 1200 s of audio — 4.65× realtime** (second run: 254 s) |
| `DYNAMIC_BATCHING` | **accepted**, echoed back in the operation metadata |
| `progressPercent` | **populated** — 26 / 52 / 78 % over thirteen polls |
| `totalBilledDuration` | `"1200s"`, exactly the audio duration |
| cost | $0.06, against $0.32 for the same audio via sync |

Two of those retire risks. **Risk 3 was wrong**: the plan assumed `progressPercent` might
always be absent and designed an elapsed-time fallback, and Phase 11 can show a real bar.
**Risk 2 now has a number** rather than two samples from someone else's spike, and every
batch run writes its own into `runs.pipeline.batch.latencyMs`, so it stops being an
argument as soon as the product is used. 4.65× is a little slower than S3's 5.9×; the
routing conclusion is untouched, since chunked sync would have done this file in well under
a minute.

**The crash test passes.** `kill -9` immediately after the CLI prints `[persisted]`, then
`thibi runs resume <id>`: it re-polled the same operation, wrote the transcript and swept
the prefix, and Google's operations list holds **exactly one** operation for that run's
input URI. That is the whole point of the ordering, demonstrated rather than argued.

### And then the number that looked too big

20 minutes of audio normalized to **136 MB**. 16 kHz mono should be a fraction of that.

**`loudnorm` runs internally at 192 kHz and emits at its own rate**, so
`…,aresample=16000,loudnorm=…` silently discards the resample in front of it. The derivative
kind is called `norm_16k_mono_flac` and it had **never once produced 16 kHz** — not in this
phase, in Phase 1, or in any sync run since. Nothing failed, which is exactly why it
survived: Google accepts 192 kHz FLAC and transcribes it correctly.

With a trailing `aresample=16000` the same input is **22.7 MB, 6.0× smaller**. That applies
to every sync chunk, every staged upload, and every byte of Google's 10 MB per-request cap
that the chunk planner budgets against — so Phase 1's chunk counts on long files were
inflated the whole time. It also means the downmix finding the file quotes from the old app,
measured on real 16 kHz audio, was not actually in force. `RECIPE_VERSION` derives from the
filter string, so the fix invalidates cached derivatives by itself; the mechanism designed
in Phase 1 for exactly this did its job.

The bit depth was briefly a suspect and is not guilty: FLAC negotiates s16 against
`loudnorm`'s float output regardless of a 24-bit source, so both the broken and fixed
outputs are 16-bit. Only the rate was wrong.

A second, smaller bug from the same session: `persistResult` did `pipeline = $4`, replacing
the column wholesale. Harmless while `transcribe.ts` was its only writer, and wrong the
moment `persistOperation` started writing `pipeline.batch` before the first poll — the final
update deleted the operation record and the latency with it. Found by querying
`pipeline->'batch'` after the first successful run and getting null.

Eighteen commits had accumulated across three local branches with nothing pushed. The
branches turned out to be a linear stack rather than divergent lines of work —
`plans/initial-design` → `phase-0/monorepo-and-registry` → `phase-2/batch-recognize`, each a
strict superset of the one below — so they went up as three stacked PRs, each reviewable as
its own diff, merged bottom-up into `main`:
[#1](https://github.com/Thibico/thibi-transcribe/pull/1) plans,
[#2](https://github.com/Thibico/thibi-transcribe/pull/2) Phases 0 and 1,
[#3](https://github.com/Thibico/thibi-transcribe/pull/3) Phase 2.

Merge commits rather than squashes, because squashing #1 would have rewritten the commits
#2 was built on. The commit messages are the reasoning record; flattening them would throw
away the thing this project keeps them for.

## `.github/workflows/ci.yml` — MinIO moves off the Bitnami image

**CI had never run.** Not once. The workflow is only discovered once it is on a branch
GitHub knows about, so the entire history to this point was verified locally and by nothing
else. Its first two runs, on the merges of #2 and #3, both failed in 23 and 29 seconds —
at `Initialize containers`, before a single test executed:

```
docker pull bitnami/minio:latest
Error response from daemon: manifest for bitnami/minio:latest not found
```

Not a flake and not fixable by retrying. Docker Hub reports **0 tags** on `bitnami/minio`:
Bitnami emptied its free catalogue in August 2025 and moved the images to `bitnamilegacy/`,
which is frozen at 2025-08-19. The tag cannot come back.

The replacement is `minio/minio` — the image `infra/compose.dev.yml` was already using, so
this also closes a gap where CI and dev were pulling different MinIOs to test the same code.
It cannot be a service container: those take `options` (docker run flags) but no command,
and `minio/minio` exits printing help unless given `server /data`. Bitnami's image started a
server unprompted, which is the only reason the service-container shape ever worked here —
worth writing down, because "just swap the image" is the obvious fix and it does not work.

Two things the swap dragged with it:

- **The bucket has to be created explicitly.** `TEST_S3_BUCKET` used to arrive via
  `MINIO_DEFAULT_BUCKETS`, a Bitnami extension the official image does not have, and nothing
  in the suite creates it — there is no `mc mb` and no `createBucket` anywhere in
  `packages/`. So the step ends with the same `mc mb --ignore-existing` one-shot that
  `compose.dev.yml` already runs.
- **`mc` reaches MinIO by container name on a user-defined network**, not `--network host`.
  Host networking is Linux-only, so the host-networked version would have been unverifiable
  on the laptop that has to change it next.

**Verified rather than asserted**, which caught a real problem in the check itself. The first
local run reported `minio ready after 1 attempt` — against the dev-compose MinIO already
holding port 9000, not the container under test. A readiness probe that passes because
something else is listening is exactly the failure mode this step exists to prevent. Re-run
on an isolated port, MinIO came up in 5 attempts (~8 s), `mc` created the bucket, and the
storage contract suite ran against it: **42 passed, including the presigned GET**.
