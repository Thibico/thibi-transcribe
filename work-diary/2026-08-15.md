# 2026-08-15 — Phase 9: the handlers, and the first real transcript through a worker

Executed against [phase 9](../plans/phase-09-queue-and-worker.md), on branch `phase-9/handlers`.

Three commits. Yesterday ended with a worker that booted, subscribed to seven queues, recovered
on restart, drained on SIGTERM — and transcribed nothing, because `createHandlerRegistry()`
returned `{}` and, separately, nothing anywhere called `materialisePlan`. Today it transcribed a
sixteen-minute Burmese interview, and then survived being killed in the middle of one.

---

## `main` was red, and the check that failed was one of ours

**[`20be57a`](https://github.com/Thibico/thibi-transcribe/commit/20be57a) — Give the Google defaults and the provider builder one home each**

Before anything else: CI had been failing since PR #37 merged, on *No region doctrine* — the
grep that allows exactly one file in source to name a Google region. `apps/worker/src/main.ts`
named one inline as `googleDefaults: { region: 'asia-southeast1', model: 'chirp_2' }`.

The grep is right and the second copy is the defect, but the interesting part is *why* the
second copy existed. The constants lived in `apps/cli/src/config.ts`, so the worker had nowhere
to import them from, and writing them out was the path of least resistance. They now live in
`apps/runtime/src/config.ts` — the composition root both apps already share — `buildContext`
defaults `googleDefaults` rather than demanding it, and the CI exclusion moved with them. There
is no longer anywhere else to put a copy.

The same argument, applied one step ahead of the same mistake: `apps/cli/src/providers.ts`
became `apps/runtime/src/providers.ts`. An `asr.chunk` handler gets a run row naming a provider
and a model and has to turn that into something it can call; a second `buildProvider` in
`apps/worker` would have been the retry-table drift this project paid for two sittings ago.

## Five handlers, and something to give them work

**[`4f198ae`](https://github.com/Thibico/thibi-transcribe/commit/4f198ae) — Give the worker handlers, and give something the job of creating a DAG**

`media.probe`, `media.normalize`, `plan.chunks`, `asr.chunk`, `normalize.text` — which together
are a complete chunked run and deliberately nothing more. The other ten kinds have no handler
because `thibi runs start` plans none of them, so the gap is visible in the plan rather than in
`/admin/queue` at three in the morning.

`thibi runs start <jobId>` is the counterpart to `thibi transcribe`, and the difference between
them is the whole point of the phase: `transcribe` drives every stage in one process and dies
with the laptop lid; `runs start` creates the run, plans its DAG, rings the doorbell and
returns.

### The correction that mattered: where the seam merge puts persistence

The plan says twice — in §9 and in the porting table — that segments are inserted per chunk, and
sites the old app's comment in `handlers/asr-chunk.ts`:

> *Insert per chunk rather than at the end, so a long file shows partial results as it goes and
> a late failure doesn't discard earlier work.*

The second clause is correct and survives. The first cannot, and the reason is a feature the old
app did not have. Chunks start 1200 ms early so the LCS merge can drop the words said twice at
each seam — so a chunk's **leading** words are not final until its predecessor's are known. Rows
written per chunk would have to be deleted and renumbered at every seam, on the one table whose
defining rule is that the machine's output is never overwritten.

So `asr.chunk` writes its parsed result to `runs/{id}/results/{idx}.json` and `normalize.text`
writes the segments once, in order. Which is what the overview's own pipeline diagram —
`ASR → reconcile → normalize-text → persist` — said all along; it was the phase document that
had drifted from it.

Nothing is lost by the move and something is gained: **the artifact's existence is also the
re-billing guard**, committed before the step row. A worker killed between "the provider
answered" and "the step was marked done" finds the artifact on recovery and does not pay twice.
That turned out to be more than a nice property — see below.

Placeholder segments for dead chunks moved with it, from the dead step's handler to
`normalize.text`, which is the only thing that knows the whole timeline `segments.idx` is
assigned across.

### Two defects the tests found

**A JSON `null` is not a SQL NULL.** `createRun` wrote `JSON.stringify(probeRaw ?? null)` into a
`jsonb` column, which stores the *document* `null` — so `probe_raw is not null` was true for
every asset ever inserted, including every asset nothing had ever probed. `media.probe` asks
exactly that question to decide whether it can skip downloading a 2 GB file, so it would have
skipped always. Found because a test asserted `probed === false` on a freshly created asset and
the assertion, not the code, turned out to be the honest one.

**A job's status never left `running`.** `reconcile` is the only writer of `runs.state`, and
nothing mirrored a terminal run onto `jobs.status`. Every queue-driven run would have left its
job listed as still working, forever — a finished transcript rendered as in-progress, which is
the failure mode this phase exists to remove rather than relocate.

### Making the handler testable at all

`asr.chunk` builds its provider from the environment, which would have made it a handler no test
could reach without an API key and a network. `HandlerDeps` injects the builder instead. That is
amendment 75's question asked of new code rather than rediscovered in it: *what can no longer be
tested because of this import?*

An ESLint rule on `handlers/**` refuses `reconcileRun`, `withRetry`, `PgBossDoorbell` and
`pg-boss`, and `tests/lint-rules.test.ts` watches the rule — a rule nobody has seen fire is a
rule that might not be wired up.

## Then it ran, and the first run transcribed nothing and reported success

**[`17396fb`](https://github.com/Thibico/thibi-transcribe/commit/17396fb) — Run a real file through the worker, and find the bug that only running finds**

Sixteen minutes of Burmese, twenty chunks, `chirp_2`. The worker booted, probed, normalized,
planned twenty chunks, transcribed all twenty against Google — and the log's *first* line of
work was `persist: written (segments=0 words=0)`.

`startRun` planned the DAG with `chunkCount = 0`. That emitted zero `asr.chunk` shards **and**
`normalize.text`, whose `['asr.chunk','*']` dependency then resolved to an empty array. A step
with no dependencies is a root. The reconciler promoted it on the first tick, a worker assembled
a transcript out of nothing, and the run reached `done` at progress 1 with zero segments while
twenty chunks were still queued behind it. $0.27, nothing kept.

Two fixes, both about the same conflation:

**`null` is not `0`.** "I do not know how many chunks there are" and "there are no chunks" are
different statements. `planRun` takes `number | null`, and on `null` it stops after
`plan.chunks` — everything past that point depends, directly or through `normalize.text`, on a
wildcard with nothing to resolve to. `batch` is exempt: its ASR steps are not sharded, so the
count it does not know is not one it needs. **The reconciler cannot make this distinction
itself**: by the time it reads `depends_on` the array is `uuid[]`, and a collapsed wildcard is
indistinguishable from a genuine root. The planner is the last place that still knows.

**The second pass renumbers.** `ON CONFLICT DO NOTHING` left rows from the first pass on the
first pass's ordinals once the shards were inserted ahead of them — `normalize.text` sat at
ordinal 3 beside `asr.chunk` shard 0. Ordinal order is a topological order and `reconcile` walks
it. Now `DO UPDATE SET ordinal`, guarded by `WHERE ordinal IS DISTINCT FROM` so planning stays a
genuine no-op, which is why the idempotence tests assert on `xmin` and still pass.

**The existing test asserted the bug was absent by checking only that the first pass emitted no
`asr.chunk` shards.** That was true the entire time. It now asserts what actually matters, which
is that `normalize.text` is not there either. Third sitting running in which a test that looked
right was satisfied by the broken behaviour.

### The live checklist, run rather than described

- **16m37s Burmese, 20 chunks**: 40 segments, 2553 words, 19 seams merged, no placeholders,
  `wordTimingQuality=full`, $0.2719.
- **Per-step retry without re-billing.** After the fix, `normalize.text` alone was reset and
  reassembled the entire transcript from the stored chunk artifacts. No chunk re-sent, cost
  unchanged. §9 promises this; this is it happening.
- **Crash recovery — the assertion that matters most in this phase.** A five-minute clip,
  `kill -9` with one chunk done and five running. On restart the sweep reclaimed all five at
  attempt 1, and chunks 0 and 5 — whose provider call had completed before the kill but whose
  step row had not been written — logged `chunk already transcribed; not re-sending`. Two chunks
  of audio that were already paid for were not paid for twice. Chunks 2, 3 and 4 genuinely had
  not finished and were re-sent. Run finished `done`: 12 segments, 724 words, $0.0816.
- **Drain.** SIGTERM mid-run: `graceful stop complete`, exit 0.

### Two smaller things starting it found

**`WORKER_HEALTH_PORT` defaulted to 8081, which is the sidecar's port** in this repo's own
`infra/compose.dev.yml`. The worker refused to start with `EADDRINUSE` on every box that can
diarize — which is every box the next phase cares about. Now 8090.

**Three database suites had no `beforeAll` budget**, so they inherited vitest's 10-second default
and failed whenever the machine was loaded. `constraints.test.ts` carried a comment on its
`afterAll` reading *"60 s, matching the `beforeAll` above"* — which was simply not true. All
three now say 60 s and mean it.

1256 tests across 81 files, nothing skipped, fully green.

# Second sitting — the batch path, and the state that was never reachable

Three more commits, on branch `phase-9/batch-handlers`, against
[phase 9](../plans/phase-09-queue-and-worker.md). The morning's sitting proved a chunked run
end to end. This one takes the other ASR shape — the one where the work happens on somebody
else's computer for five minutes and the worker must not sit and wait for it.

## The state the whole design rests on could not be entered

**[`863b23d`](https://github.com/Thibico/thibi-transcribe/commit/863b23d) — Make
`awaiting_external` a state a step can leave**

Before writing a single handler: `reconcile` promotes `pending` steps and re-rings `ready`
ones, and sends nothing else. So a handler returning `awaiting_external` with a `poll_after`
would have parked its step forever, holding a timestamp that no mechanism anywhere read.

The interesting part is how much correct machinery was already built around the gap. `runStep`
claims `state in ('ready','awaiting_external')`. `run_steps` carries a partial unique index on
`poll_after where state = 'awaiting_external'`. `StepResult` has the variant, with `pollAfter`
and `deadlineAt` on it. `recover.ts` has a statement dedicated to nudging those steps. Every
one of those was written for a caller that did not exist, and the handoff note has said for
three sittings that the state had "never been exercised" — which was too generous. It was not
reachable.

`reconcile` now sends them too, with `poll_after` as pg-boss's `startAfter`, so the wait is
held by the queue rather than by a worker slot. Predicated on `poll_after` being set, and that
guard is load-bearing rather than tidy: a re-ring with no `startAfter` polls instantly, returns
`awaiting_external`, and is rung again — a tight loop against a provider.

The same commit corrects `recover.ts` from the other end. `nudgeExternalWork` is
`poll_after = least(poll_after, now())`, which drags a *future* poll forward. On boot that is
the point. On the 60-second tick it would pull every scheduled poll back to now once a minute,
so a capped 30 s → 300 s backoff becomes a flat 60 s and a two-hour operation makes 120
requests against a quota the sync path also needs. It matched zero rows on every tick until
these handlers existed, which is why nothing had noticed. Amendments 97 and 98.

## The plan's §7 could not work, for a reason that is not about batching

**[`6c15b68`](https://github.com/Thibico/thibi-transcribe/commit/6c15b68) — Give the worker the
batch ASR path, and correct where the waiting lives**

§7 has `asr.batch.submit` return `awaiting_external` carrying the operation name, and a
separate `asr.poll` step do the polling. Those two sentences contradict each other. `asr.poll`
**depends on** the submit step, and the reconciler satisfies a dependency only on `done` or
`skipped` — so a submit parked in `awaiting_external` would be re-claimed by its own re-ring,
hit its idempotence guard, return `awaiting_external` again, and poll nothing forever while
`asr.poll` sat `pending` behind it. The sketch predates `StepResult` and the reconciler and
quietly assumes one step where §2's own kind table lists three.

The wait moves to `asr.poll`, which is where §6's queue routing already assumed it was: that
kind has its own queue precisely so a sub-second poll never queues behind a forty-minute
diarize, and a submit holding the wait would have done it from `asr.cloud`.

That changes what guards the double bill. `step.externalRef` cannot be it, because a `done`
result has no field to set it from. The persisted `BatchOp` is better anyway:
`persistOperation` commits before the step row, so a stored operation is the durable evidence
that Google already has the audio and the money is already committed. Exactly the shape of
amendment 96's artifact guard, arrived at independently and for the same reason — *what is
durable is what proves the spend*, because the step's own state is not durable at the moment
it matters.

`asr.fetch` writes no segments. It writes `runs/{id}/results/0.json`, the same artifact
`asr.chunk` writes per shard, and `normalize.text` assembles it. The plan gives that step the
word "persists", which would have meant a second copy of `normalize.text` exercised only by
batch runs and noticed by nobody when it went stale. One artifact means the batch path gets the
Zawgyi normalization, the `text_raw` audit trail, the placeholder rule and the `usage_records`
row for free.

Two smaller decisions worth their sentences. `staging.cleanup` sweeps the GCS prefix and
nothing in our own object store: it and `normalize.text` are both dependents of `asr.fetch`, so
they run concurrently, and a version that also deleted the chunk artifact would occasionally
delete the file `normalize.text` was about to read. And a failed operation fails the step
non-retryably even when Google marks the failure retryable — `status.retryable` means
*re-submitting* is worth something, and this step does not submit, so eight more polls would
ask the same question eight times over forty minutes of backoff.

## Then it was pointed at a real recording

**[`ecc31dc`](https://github.com/Thibico/thibi-transcribe/commit/ecc31dc) — Run a real batch
operation through the worker, and find what only running finds**

Sixteen minutes of Burmese, submitted by a worker to `batchRecognize` in `asia-southeast1`,
`dynamicBatching: true`. Five polls, 317761 ms of latency, 35 segments, 2364 words, no
placeholders, `wordTimingQuality=full`, staging swept, run `done`. Mid-operation, at 63%,
`kill -9`. On restart: `reclaimed=0 nudged=1` — the poll step correctly *not* treated as a
stale lease — and the same operation resumed and finished. `submitBatch` was called once.

Four findings, and the corrections are the useful part.

**A batch run's cost was 5.3× too high, sitting next to a correct number.** `runs.cost_usd`
said $0.2658; `usage_records` said $0.0499 for the same audio. `provider.costModel(mode)`
**ignores the mode it is given** — Google's implementation is literally `costModel(_mode)`,
returning the sync Recognition list price of $0.016/min for everything, where a Dynamic Batch
minute is $0.003. It had never mattered because the CLI's batch path prices from `recordUsage`
and never calls `costModel`; `asr.fetch` is its first batch caller. `normalize.text` now writes
the run's cost from what `recordUsage` resolved out of the `rates` table — the number carrying
a SKU, a catalogue and a read date — and falls back to the estimate only when no rate exists,
because "we do not know what this cost" must not become $0.00. Verified live: $0.04985 in both
places, against Google's own reported `totalBilledDuration` of 997s.

**The boot nudge does not do what amendment 92 says it does.** After the kill,
`run_steps.poll_after` was 35 seconds in the past — the nudge had written it — while the queued
pg-boss job still started 27 seconds in the *future*. Polling never bumps `attempt`, so every
poll sends under the same singleton key; `reconcile` had already queued the next poll before
the crash; the boot re-ring hit the `short` policy's one-queued-job-per-key rule and was
dropped. The row says "poll now", the queue says "poll in 27 seconds", and **the queue wins**.
So the nudge is a repair for a doorbell the queue *lost*, not an accelerator. Still worth
having in that role, and the claim that a restart costs nothing rather than one poll cycle is
now corrected rather than repeated. Latency only — never correctness, never money.

**`progressPercent` is absent on the first two polls and populated from the third**, at 31%
then 63%. §7 says it is populated, measured 26/52/78, and treats the 0.2 fallback as being for
a provider that omits it entirely. On this operation the fallback is what the timeline showed
for the first minute of a five-minute wait. The behaviour is right — it is never fabricated
upward — but the plan's confidence in the measurement was.

**`normalize.text` is not idempotent per run.** Resetting it alone over a run that still had
its segments failed on `segments_run_idx_live`, the partial unique index that exists precisely
so superseded rows can be history. The `superseded_at` / `superseded_by` columns are in the
schema and `writeTranscript` does not use them. Pre-existing, shared with the chunked path, and
recorded as debt rather than fixed with a half-considered supersede at the end of a sitting.
With the segments cleared, the retry reassembled the entire transcript from the stored artifact
with no provider call — which is the property that actually mattered.

1269 tests across 82 files, nothing skipped, with Postgres, MinIO and the sidecar up. Was 1256
across 81.
