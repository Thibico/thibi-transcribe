## Sitting 2 — Phase 4a

Executes [`plans/phase-04-whisper-providers.md`](../plans/phase-04-whisper-providers.md), whose

### What shipped

`ada4d81` — **script integrity** in `@thibi/core`. The fraction of a transcript's letters written
in the script the language actually uses. It ships a phase early, ahead of the harness that will
use it, so the Groq case is a number in CI rather than a paragraph in a research note.

`90f8d26` — **the shared transport and the two providers.** One `whisper-http.ts`; `openai.ts` and
`groq.ts` hold model tables, limits and capability facts and no HTTP at all. Neither holds a
language mapping either — the code on the wire comes from the matrix's `providerCode`, because
deriving it gets `fil-PH` wrong (Whisper's tokenizer predates the rename to Filipino and wants
`tl`).

`4c84924` — **`chooseProvider`** in `@thibi/languages`, so Phase 11's picker can render the same
decision from a browser, plus the matrix change discussed below.

`b9f9df3` — **the CLI**: `thibi providers list --language`, `--force-unsupported`,
`--no-word-timestamps`, a shared `buildProvider`, and rate rows for both vendors.

### The corrections, which are the useful part

**1. `attach-words` leaked words backwards across contiguous boundaries.** The plan specified
containment by start time with a 20 ms tolerance and first-match-wins. That is wrong, and only a
*recorded* response showed why: real `verbose_json` segments abut exactly. In
`openai-verbose-json-en.json`, segment 1 ends at 7.239999771118164 s and segment 2 begins at
7.239999771118164 s, and the word "statement" starts on that boundary. A symmetric tolerance makes
neighbours overlap by 2·eps, the word goes to segment 1, and segment 2 gets no words at all —
`wordTimingQuality` fell from `full` to `partial` on a four-segment response, and on an hour of
audio it would strip the timings off a segment at every boundary. Now two passes: strict
containment first, tolerance only for words no segment contains. A hand-written fixture with tidy
round numbers could never have produced this.

**2. The plan's hallucination guard could never have fired.** It says drop segments where
`no_speech_prob > 0.6 && text.trim().length < 3` — "the 'Thank you.' that Whisper emits over
trailing silence". "Thank you." is ten characters. The rule contradicts the phrase it exists for
inside the same sentence. Writing the test surfaced it. `no_speech_prob` is the detector and the
length is only the rail that stops one uncertain number deleting a paragraph, so the cap is now
30, both conditions still required, with a test that a genuine `"Yes."` at low `no_speech_prob`
survives — deleting one-word answers from an interview would be a worse bug than the one fixed.

**3. Groq returned 96 words spanning 30.4 seconds for 2 seconds of audio.** Found by running
`thibi transcribe --force-unsupported --raw-dir`, not by any test. The normalized Burmese probe
clip hit a repetition loop: `duration: 2`, one segment ending at 2 s, and word timestamps fifteen
times longer than the audio. The unattached counter had already caught them so nothing bad reached
the transcript — but "63 words could not be matched" invites a hunt for a matcher bug, so there is
now a `timings_beyond_audio` warning that names the provider as the cause.

**4. A Definition-of-done item I would have claimed as done.** `resolveModelWithReason` correctly
returns `null` with a printable reason for the seven `gpt-4o-transcribe`-only languages, and its
unit test passed throughout. The CLI then wrote `?? OPENAI_DEFAULT_MODEL` and threw the null away,
so `--lang bn-IN` sent whisper-1 and the user got `400 Language 'bn' is not supported.` — told the
language is unsupported when it is supported and merely cannot carry timestamps. The unit test was
testing the resolver; the bug was in the line that discarded its answer. It now fails before the
request with the reason and the next command to type.

### The Groq finding got worse

The 2026-07-30 research recorded Myanmar-script non-words for `language=my` and romanised Latin on
autodetect. Re-run on the committed 2 s clip on 2026-08-11: **Khmer script** for `language=my`,
and **Vietnamese** on autodetect — with `language: "Vietnamese"` in the body. Two clips, two
dates, three distinct failure modes, all HTTP 200, all with `avg_logprob` ≈ −0.6 and
`no_speech_prob` ≈ 0.05, numerically indistinguishable from the correct English control run
through the same model minutes earlier.

That last point is the one worth carrying: **nothing in the response envelope separates a correct
transcript from a confident wrong-language one.** It is also a useful check on the new metric —
script integrity caught both of these because Khmer is not Myanmar, but it missed the 2026-07-30
`language=my` case because Myanmar-script non-words are still Myanmar script. It is a screen for
wrong-alphabet output and never a guarantee, and the test asserts the miss so nobody later reads a
1.00 as a pass.

### Refusing a Definition-of-done item

The plan asks for every unmeasured Groq code outside OpenAI's list to be marked
`supported: false, evidence: "assumed"`. `matrix-overrides.json` — written in Phase 0, before this
plan was executed — already refuses that: *"Marking a whole family unsupported on a hunch would be
the same error as marking it supported on a status code, in the other direction."* Twenty-four
fabricated negative findings are worth no more than twenty-four fabricated positive ones.

Instead, `verdict: "suspected"` widened from 5 codes to all **24 that Groq accepts and no OpenAI
model does** — the set the one measured failure came out of. `supported` untouched, the picker
warns, `chooseProvider` never lets a suspected row outrank a settled one, and Phase 5 promotes or
demotes each with a number attached. Recorded as amendment 32.

### Numbers now measured that were previously guessed

Everything below replaced either a guess of mine or a figure inherited from the plan.

| Thing | Was | Is | How |
|---|---|---|---|
| OpenAI RPM | a conservative guess of 100 | **5000/min** | `x-ratelimit-limit-requests: 5000`, 12 ms reset, off a live response |
| Groq limits | "20 rpm" | **2000 requests/day** and **7200 audio-seconds/hour** | live headers; 43.2 s reset per request is 86400/2000 |
| Groq dev-tier size cap | 25 MB assumed | **100 MB** (25 MB free) | GroqCloud docs |
| Prices | none | $0.006/min OpenAI, $0.111/hour Groq | each vendor's pricing page, dated |
| 16 kHz mono FLAC bitrate | 18.9 KB/s from one clip | **20.8 KB/s** on a second, unrelated clip | corroborates amendment 24, and kills the plan's 110 KB/s for good |

The bitrate corroboration matters beyond tidiness: it is what makes the 25 MB cap bind at ~22
minutes instead of ~230 s, which turns the sync chunk duration from a consequence into a choice.
Chosen: **600 s**, reasoned beside the constant in `openai.ts` — a lost chunk costs ten minutes
rather than twenty-two, six chunks an hour give four concurrent requests something to do, and
twice the measured density still fits inside 25 MB.

## Sitting 3 — Phase 3 begun: the probe first, then the reconciler

Executed against [`plans/phase-03-diarization.md`](../plans/phase-03-diarization.md).

### The day-one probe, and the coin flip

Phase 3's plan opened with an instruction rather than a design: **probe
`gpt-4o-transcribe-diarize` before committing to the sidecar as the only path.** Phase 4a had
spotted the model in OpenAI's docs, and if it worked most of Phase 3 would have been unnecessary.
It ran before a line of Phase 3 code was written, and is recorded as spike
[S7](../spikes/RESULTS.md#s7--is-a-hosted-diarizing-asr-an-alternative-to-running-pyannote-ourselves).

The answer splits in two, and keeping the halves apart is the whole point.

**The diarization is good.** Scoring it needed a reference, so
[`s7-make-2spk.mjs`](../spikes/s7-make-2spk.mjs) builds one: each turn synthesised with a
different macOS voice and concatenated with a known gap, which makes the cumulative offsets the
RTTM. No hand-labelling, no judgement about where a turn starts. Against it the model found 2 of
2 speakers with **0.0% confusion**, DER 9.2% — all of it *miss*, speech clipped at segment edges —
and a **63 ms median boundary error**. Better than anything measured here on our own hardware.

**Everything around it lands on the long tail.** `language=my` is a flat HTTP 400. A sweep of 142
codes leaves **39 of our 116 seeded locales with no code the endpoint will accept at all** —
Khmer, Lao, Pashto, Punjabi, Sinhala, Uzbek, Cebuano, Sorani and most of the African set. There is
a hard **1400 s (23 m 20 s) ceiling**, so a one-hour interview cannot go through it in any
language. And it returns **no word timings at any granularity**; `timestamp_granularities[]=word`
is accepted and silently ignored.

**The finding worth carrying forward is about method.** The sweep sent `mya` — ISO-639-3, accepted
where `my` is not — and got back `ကုန်နံ့ရည်ကုသ ုစာပျောက်ခွဲမပီဘူး`, 31 of 32 characters in Myanmar
script. **One probe would have concluded that Burmese works.** Twenty identical requests returned
**twenty distinct transcripts and not one in Myanmar script**, wandering across Vietnamese, Thai,
Chinese and twice into fluent English about nothing. It was 1 in 21.

Phase 4a's lesson was that a wrong transcript can look healthy. This is worse: the *same request*
is right occasionally, so a single sample is not weak evidence — it is a coin flip presented as a
measurement. [`s7-mya-stability.mjs`](../spikes/s7-mya-stability.mjs) is the shape any future
language claim has to take. Amendments 35 and 36; 34 closed.

The verdict is **FAIL for this product, not in general**. For an English-language newsroom on
sub-23-minute recordings the model is a serious option. That is exactly why it had to be measured
per language rather than argued about.

One thing S7 did *not* get: throughput at length. The 23-minute head-to-head against S6's podcast
was submitted three times and never returned, the last attempt abandoned after 38 minutes. The
short-clip rate of 2.3–3.0× realtime therefore does not extrapolate, and the spike says so rather
than estimating from it. (Two of those three deaths were ours — a synchronous endpoint holding one
connection open outlives undici's 300 s headers timeout, and `UND_ERR_HEADERS_TIMEOUT` reads
exactly like a provider failure. The instrument posts over `node:https` now.)

### The reconciler, and two bugs in the reference implementation

With the sidecar confirmed as the path, the pure half of Phase 3 got built first: everything that
turns turns into attribution, with no network and no database in the way.

The **Hungarian solver** in `packages/core/src/algo/hungarian.ts` is hand-written — `core` may
depend on nothing, `munkres-js` is unmaintained, and real matrices are at most 12×12. It failed
twice while being written and **both failures were in the brute-force reference, not the solver.**
The reference pruned on `total >= best`, which is invalid with negative costs — and the identity
matcher passes `-overlapMs` precisely so minimising cost maximises overlap — so it reported the
solver wrong on 8×8 when the solver had found a *better* assignment. Removing the prune then left
`best = total` unguarded. The hand-worked "greedy trap" expectation was also wrong: the optimum is
104, not 105. Worth recording because all three looked like solver bugs.

`reconcile.ts` implements the plan's five steps, with three deviations the plan had not
considered:

- **The moving cursor is only valid on time-sorted words, and nothing said so.** Words arrive in
  `(segment idx, word idx)` order, which is usually time order and is not guaranteed to be across
  a merged chunk seam. An out-of-order word would be matched against already-retired turns and
  come back *wrong* rather than erroring. Sorting now happens once, in a top-level `reconcile()`,
  because `medianSmooth`'s notion of "neighbour" is temporal too.
- **Zero-length words.** Providers emit `start === end`, and under a plain overlap test such a
  word overlaps nothing and falls through to `nearest` or to null for no reason but a timing quirk.
- **`intervalFallback` could return a purity above 1**, because same-speaker overlapping turns
  accumulate past the segment's own span.

The two fixtures that matter most are `interjection-short-but-certain` and
`interjection-long-but-uncertain`. `interjection-genuine` alone **cannot** protect the median
filter's guards: both guards refuse that case, so deleting either one still passes. The pair
isolates them, and a separate test disables each guard by moving its threshold and asserts the
flip *does* then happen — which is what proves the fixtures are load-bearing rather than
incidentally green.

`interjection-genuine` also produced a number worth having in writing: its segment purity is
1100/1720 = **0.64, just above the 0.6 review threshold**, so a segment in which a second speaker
genuinely spoke is not flagged. 0.6 was chosen, not measured. Recorded in the fixture rather than
left for Phase 5 to be surprised by.

### The schema, and a plan that predated the code again

`0003_speakers.sql` adds three tables, two foreign keys and one partial index — **not** the five
columns Phase 3 §4 specifies. `segments.speaker_id`, `speaker_purity`, `needs_speaker_review` and
`words.speaker_id` have been in `0000_init.sql` since Phase 1 with a `-- FK added in Phase 3` note.
Fourth phase running where reading the deliverables table against the code first was worth the two
minutes. Amendment 37.

Both FKs are `on delete set null`, never `cascade`: deleting a speaker must orphan the
*attribution* and never the transcript. Tested from both ends, including that a `speaker_turns`
row survives with its `raw_key` intact — without which "the transcript says Daw Khin and she never
said that" is uninvestigable, because the evidence would have been overwritten by the conclusion.

### The sidecar

`services/sidecar` — FastAPI, four routes, 30 pytest tests. The shaping decision: **the suite does
not import torch.** The `Pipeline` protocol is structural so a canned pipeline drives the same
hook the real one drives, which puts idempotency, the single slot, cancellation, the failure
taxonomy and temp-file cleanup under test without a 2 GB dependency and a gated download. The
audio *is* real, because every case being tested is about the fetch.

Writing those tests found a live bug in the production path: `realtime_factor` rounded
`compute_ms` before dividing, so a sub-millisecond run divides by zero and the `or 0.0` fallback
publishes a factor of **0.0** — which then enters `/health`'s rolling median and reports the
machine as infinitely slow. Real diarizations are never that fast. The canned pipeline is. A
sentinel that only misbehaves where nobody looks is the kind that survives to production.

### Verification

`pnpm build && pnpm typecheck && pnpm lint && pnpm test` — **605 tests, none skipped**, with
Postgres and MinIO up. 30 sidecar pytest tests pass separately. One flaky test of my own making
was removed: a wall-clock assertion on the 64×64 Hungarian solve passed in isolation and failed
inside the full 36-file parallel run, which makes it a test of machine load rather than of the
function.

**Not verified: the sidecar image build.** It was still pulling torch when the session ended, so
whether `pyannote.audio>=4.0` resolves against these pins is unknown and is the first thing to
check next time.
