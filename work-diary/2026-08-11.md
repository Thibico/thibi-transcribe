### The corrections, which are the useful part

**1. `attach-words` leaked words backwards across contiguous boundaries.** The plan specified
containment by start time with a 20 ms tolerance and first-match-wins. That is wrong, and only a
*recorded* response showed why: real `verbose_json` segments abut exactly. In
`openai-verbose-json-en.json`, segment 1 ends at 7.239999771118164 s and segment 2 begins at
7.239999771118164 s, and the word "statement" starts on that boundary. A symmetric tolerance makes
neighbours overlap by 2·eps, the word goes to segment 1, and segment 2 gets no words at all —
`wordTimingQuality` fell from `full` to `partial` on a four-segment response, and on an hour of
audio it would strip the timings off a segment at every boundary. Now two passes: strict
containment first, tolerance only for words no segment contains. A hand-written fixture with tidy
round numbers could never have produced this.

**2. The plan's hallucination guard could never have fired.** It says drop segments where
`no_speech_prob > 0.6 && text.trim().length < 3` — "the 'Thank you.' that Whisper emits over
trailing silence". "Thank you." is ten characters. The rule contradicts the phrase it exists for
inside the same sentence. Writing the test surfaced it. `no_speech_prob` is the detector and the
length is only the rail that stops one uncertain number deleting a paragraph, so the cap is now
30, both conditions still required, with a test that a genuine `"Yes."` at low `no_speech_prob`
survives — deleting one-word answers from an interview would be a worse bug than the one fixed.

**3. Groq returned 96 words spanning 30.4 seconds for 2 seconds of audio.** Found by running
`thibi transcribe --force-unsupported --raw-dir`, not by any test. The normalized Burmese probe
clip hit a repetition loop: `duration: 2`, one segment ending at 2 s, and word timestamps fifteen
times longer than the audio. The unattached counter had already caught them so nothing bad reached
the transcript — but "63 words could not be matched" invites a hunt for a matcher bug, so there is
now a `timings_beyond_audio` warning that names the provider as the cause.

**4. A Definition-of-done item I would have claimed as done.** `resolveModelWithReason` correctly
returns `null` with a printable reason for the seven `gpt-4o-transcribe`-only languages, and its
unit test passed throughout. The CLI then wrote `?? OPENAI_DEFAULT_MODEL` and threw the null away,
so `--lang bn-IN` sent whisper-1 and the user got `400 Language 'bn' is not supported.` — told the
language is unsupported when it is supported and merely cannot carry timestamps. The unit test was
testing the resolver; the bug was in the line that discarded its answer. It now fails before the
request with the reason and the next command to type.

### The Groq finding got worse

The 2026-07-30 research recorded Myanmar-script non-words for `language=my` and romanised Latin on
autodetect. Re-run on the committed 2 s clip on 2026-08-11: **Khmer script** for `language=my`,
and **Vietnamese** on autodetect — with `language: "Vietnamese"` in the body. Two clips, two
dates, three distinct failure modes, all HTTP 200, all with `avg_logprob` ≈ −0.6 and
`no_speech_prob` ≈ 0.05, numerically indistinguishable from the correct English control run
through the same model minutes earlier.

That last point is the one worth carrying: **nothing in the response envelope separates a correct
transcript from a confident wrong-language one.** It is also a useful check on the new metric —
script integrity caught both of these because Khmer is not Myanmar, but it missed the 2026-07-30
`language=my` case because Myanmar-script non-words are still Myanmar script. It is a screen for
wrong-alphabet output and never a guarantee, and the test asserts the miss so nobody later reads a
1.00 as a pass.

### Refusing a Definition-of-done item

The plan asks for every unmeasured Groq code outside OpenAI's list to be marked
`supported: false, evidence: "assumed"`. `matrix-overrides.json` — written in Phase 0, before this
plan was executed — already refuses that: *"Marking a whole family unsupported on a hunch would be
the same error as marking it supported on a status code, in the other direction."* Twenty-four
fabricated negative findings are worth no more than twenty-four fabricated positive ones.

Instead, `verdict: "suspected"` widened from 5 codes to all **24 that Groq accepts and no OpenAI
model does** — the set the one measured failure came out of. `supported` untouched, the picker
warns, `chooseProvider` never lets a suspected row outrank a settled one, and Phase 5 promotes or
demotes each with a number attached. Recorded as amendment 32.

### Numbers now measured that were previously guessed

Everything below replaced either a guess of mine or a figure inherited from the plan.

| Thing | Was | Is | How |
|---|---|---|---|
| OpenAI RPM | a conservative guess of 100 | **5000/min** | `x-ratelimit-limit-requests: 5000`, 12 ms reset, off a live response |
| Groq limits | "20 rpm" | **2000 requests/day** and **7200 audio-seconds/hour** | live headers; 43.2 s reset per request is 86400/2000 |
| Groq dev-tier size cap | 25 MB assumed | **100 MB** (25 MB free) | GroqCloud docs |
| Prices | none | $0.006/min OpenAI, $0.111/hour Groq | each vendor's pricing page, dated |
| 16 kHz mono FLAC bitrate | 18.9 KB/s from one clip | **20.8 KB/s** on a second, unrelated clip | corroborates amendment 24, and kills the plan's 110 KB/s for good |

The bitrate corroboration matters beyond tidiness: it is what makes the 25 MB cap bind at ~22
minutes instead of ~230 s, which turns the sync chunk duration from a consequence into a choice.
Chosen: **600 s**, reasoned beside the constant in `openai.ts` — a lost chunk costs ten minutes
rather than twenty-two, six chunks an hour give four concurrent requests something to do, and
twice the measured density still fits inside 25 MB.

### An unrelated find worth a probe

OpenAI's docs now describe **`gpt-4o-transcribe-diarize`** with a `diarized_json` format. Phase 3
is built on diarization meaning pyannote on our own hardware at ~1 h 40 m per audio-hour (spike
S6). A hosted diarizing ASR is a `DiarizationSource` that did not exist when that premise was
formed. Nothing about it is measured — no language coverage, no quality, no price — but one probe
run is cheap next to building the wrong thing, and a note now sits at the top of Phase 3's Risks.
