## The third long-async pair, and the third time §7 was wrong the same way

**[`7ff4ded`](https://github.com/Thibico/thibi-transcribe/commit/7ff4ded) — Give the worker the
diarize trio, and close the hole two good fixes opened**

Phase 3 did most of this work already, and it is worth saying how much: `PyannoteSource`, the
word↔turn reconciler, `persistDiarization` with its identity matching, the failure recorder.
Its `DiarizeHandle` even carries the comment *"JSON-only, and for the same reason `BatchOp` is
in Phase 2: Phase 9 persists this between a submit and a poll that may happen in different
processes."* Written three phases early, and correct. Nothing under `diarize/` changed except
one new file for the two things that must now outlive a worker.

The correction was the same one the batch pair needed. §7 has `diarize` return
`awaiting_external`; it cannot, because `diarize.poll` depends on it and only `done` or
`skipped` satisfies a dependency. That is the third time this sitting-pair that a plan sketch
written before `StepResult` existed has assumed one step where its own tables list two.

The *second* §7 error is more interesting because it is about a guarantee rather than a
mechanism. The plan specifies `idempotency_key: step.id` on the submit, "so a re-delivered
doorbell returns the existing task id instead of starting a second GPU job". The key Phase 3
shipped is `diarizeStepKey(runId)` — `"<runId>:diarize"` — and the difference is the whole
guarantee. The key has to be **reconstructible by a process that never saw the submit
response**. `step.id` is not: re-planning a run mints new step rows, so a resubmit under a new
key starts a second job on the one GPU, which is exactly the outcome the sentence promises to
prevent.

Three differences from the batch pair were deliberate rather than incidental, and each has a
reason attached in the code. `diarize.poll` fetches as well as polls, because the sidecar
answers on one call over the compose network where reading a `batchRecognize` output is a
bucket listing and an unbounded parse billed per operation — a fourth step would be a queue
round trip to save nothing. Its interval is flat at 15 s rather than a capped backoff, because
the sidecar is ours and a status call costs nothing, so a bar that moves is worth more than
politeness. And a 429 is `no_slot`, never an error: `diarize` has two attempts, and spending
one on two jobs happening to overlap would fail a run with nothing wrong with it.

## §6 and §7 contradict each other, and §7 wins

Building the pair settled a question the plan had left as two incompatible answers.

§6's third concurrency layer is `withGlobalSlot`, a session-scoped `pg_try_advisory_lock` held
for the duration of the work it wraps, sized by `GPU_SLOTS`. §7's rule is that a step waiting
on someone else's computer holds no worker slot. Both cannot be true of `diarize`: the submit
returns in milliseconds, so a lock taken around it releases while the GPU runs for the next
three hours, and no session lock can span `diarize` and `diarize.poll` — different steps,
usually different processes, and the holder may die.

§7 wins, because holding a worker for three hours in order to hold a lock is the precise
failure this phase exists to remove. What actually bounds diarization is the sidecar: it owns
the one slot, knows whether it is taken, and answers 429 — which maps to the `no_slot` result
§6 already specifies, and reaches it without a second mechanism that could disagree with the
first. **The authority on a resource's capacity should be the thing that has it.** `GPU_SLOTS`
is parsed and unused and should be deleted rather than left as a knob that does nothing.
`LOCAL_ASR_SLOTS` is not in the same position — `asr.chunk` on `asr.local` is one synchronous
step holding its worker for the whole transcription, so a session lock spans exactly the work
it protects — and remains worth building.

## The hole between two correct fixes

Yesterday's commit made the blanket recovery nudge boot-only, because pulling every scheduled
poll forward once a minute flattens a 30 s → 300 s backoff to a flat 60 s. The same commit
guarded the `awaiting_external` re-ring on `poll_after` being set, because a re-ring with no
`startAfter` polls instantly and spins. Both are right.

Together they leave a step sitting in `awaiting_external` with a **null** `poll_after` rung by
nothing at all until the next process restart. Neither change is wrong; the gap is between
them, which is the kind that survives review of either one. `unstrandExternalWork` now runs
every tick and sets `poll_after = now()` **only where it is null** — not a pull-forward, so it
cannot flatten a backoff, which is what lets it run where the blanket nudge may not. It should
always match zero rows, and a non-zero `unstranded` in the boot log names a handler that
returned `awaiting_external` without a `pollAfter`.

## Then it was pointed at the real sidecar, three times

**A 2-minute clip with no `SIDECAR_URL` set** — unplanned, because `.env` does not carry one
even though the container has been up for days. It was the best possible accident: `diarize`,
`diarize.poll` and `reconcile.speakers` all landed `skipped`, and the run finished `done` with
its transcript. That is Phase 3's founding invariant — diarization must never gate the
transcript — demonstrated rather than asserted, on a path nobody had thought to test.

**The same clip with the sidecar wired in** exposed a defect and is *not* a success. Polling ran
at a clean 16-second cadence for 23 polls over 9.3 minutes, reaching 63.6% — on track to finish
inside its 24-minute deadline. Then the re-ring chain stopped dead for one hour and fifty-six
minutes, and when a poll finally arrived the deadline had passed, the handler cancelled the
sidecar task (`DELETE 204`, correctly) and the step went `skipped`. The run still completed with
its transcript, so the invariant held — but a diarization that would have succeeded was lost.

**I could not explain it and did not pretend to.** What is certain: both workers stayed alive,
nothing was logged as an error, and no pg-boss job for that step exists after 10:34:39 — though
v12 deletes completed jobs, so that table is not a full record. One send before the stall got a
`start_after` 3m43s out where the handler always asks for 15 s, which is unexplained on its own.
The 30-second reconcile tick re-rings `awaiting_external` steps and evidently did not. The
`unstrandExternalWork` fix above closes the one mechanism I could prove would produce exactly
this symptom; whether it was *the* mechanism here is not established, and the handoff note says
so.

**A 30-second clip on the fixed build** ran the trio end to end: 6 polls at a clean 16-second
cadence, 13 turns, 2 speakers persisted with our durable `speaker-00`/`speaker-01` keys, 66
words attributed, run `done` at progress 1. The stall did not reproduce.

## Two things watching a real run found

**A source that honestly reports zero progress scored worse than one that reported nothing.**
`stepFraction` credited a started step 0.1 "visible, honest, and never inflated upward" — but
only when `output.progress` was absent, because `clamp01(0)` is 0. The sidecar reports
`progress: 0` for the first minutes of every pyannote run, since pyannote does not stream
progress and zero is how it says so. So the step contributed nothing to the bar for as long as
the source was being candid, which is exactly the window where a user has least other evidence
the run is alive. Now a floor rather than a default, with any genuine report above it still
winning.

**`diarize.poll` wrote no log line between submit and completion.** On a three-hour diarization
that leaves an operator with no way to tell working from wedged short of querying the database
— which is precisely what I ended up doing above. It now logs per poll, as `asr.poll` does.
