## Hosted diarization is a question again

The user reopened it. Amendment 48 closed it on 2026-08-12 and — usefully — named the trigger
for reopening rather than leaving it to judgement: *a newsroom that cannot host pyannote and
wants diarization anyway.* Three measurements taken since make that condition look less like
an edge case than it did when it was written.

**Throughput is now known rather than estimated.** 0.656× realtime on a real 16.6-minute
recording, so an hour of audio is about ninety minutes of diarization on this class of machine
(amendment 56). Every earlier figure came from clips too short to mean anything.

**The memory floor is higher than the tier table assumed.** Pyannote **plus** the resident ASR
model, not the larger of the two (amendment 54). "Can host pyannote" is a stricter test than
it looked.

**And accuracy is still unmeasured.** There is no reference RTTM, so nothing establishes that
the ninety-minute wait buys a good answer. That cuts both ways: it is an argument for looking
at alternatives, and it is the reason no alternative can yet be compared on quality. A hosted
service has no local number to beat.

## What the reopening is not

It is an evaluation, not a promise, and the distinction is the whole reason this took four
edits instead of one. Amendment 48's rule stands unchanged: **no document may describe a
hosted fallback as existing.** `scribe.ts` is still unbuilt, Phase 3 risk 2 still says the
mitigation list is one item long, and Phase 15's tier table still may not price a hosted
option. Both of those sentences were left standing and annotated rather than softened, because
an open evaluation is exactly the kind of thing that leaks into documents as a capability if
nobody says otherwise.

ElevenLabs specifically stays closed on its own merits. The question is about the category.

## The criterion amendment 48 never had to weigh

Ordered so the cheapest disqualification comes first:

1. **Long-tail language coverage.** This product exists for languages hosted ASR refuses. A
   diarizer serving only the languages we already have alternatives for solves nothing — and
   an accepted language code proves nothing, which S7 established at a cost of twenty-one
   requests.
2. **Data residency.** Self-hosted, one instance per newsroom, audio that never leaves the
   building is the premise, and a hosted diarizer breaks it for this step. **For a newsroom
   handling sensitive recordings that is disqualifying, not a trade** — so any hosted source
   ships off by default, per-instance opt-in, and named in the UI at the point of use. Never
   silently substituted when the sidecar is absent.
3. Whether it re-transcribes — §2's caveat, and it means paying for transcription twice.
4. Cost per hour and any duration cap, confirmed against the live API rather than a pricing
   page. Neither was ever established for Scribe.
5. Quality against pyannote on the same audio, which needs the reference RTTM open question 2
   is still waiting on.

Point 2 is the one this project is uniquely positioned to get wrong, because the latency
problem is loud and the residency problem is silent. The recording that produced yesterday's
measurements is exactly the kind that must not leave the building.

## The two CLI defects — and one of them was never real

Amendment 59 recorded two failures found while running the pipeline against real audio. One
was true. The other was an artefact of how I looked at it, and it had been sitting in the
canonical record for a day.

### `thibi diarize run` never exited 0

The claim was that an unset `SIDECAR_URL` produced the correct remediation message and then
exit 0, so Phase 9's queue could not distinguish "no diarization happened" from success. It
exits **2**, from `EXIT.notConfigured`, and always did.

The observation came from running `node … diarize run … | tail -40` and reading the exit
status. **A pipeline reports the last command's status**, so that was `tail`'s. Re-run with no
pipe: `exit=2`, remediation printed, no trace.

Amendment 59 is corrected in place rather than deleted, because the correction is the useful
artefact. The lesson it was written to teach — *run it* — still stands, and now cuts the other
way as well: **running it is only evidence if you look at what you actually ran.** A finding
recorded from a misread observation is worse than no finding, because the amendments table is
what later work treats as settled.

### The stack trace was real, and it was the smaller half of the problem

`THIBI_TMP_DIR` pointing at a directory that does not exist crashed with a raw `ENOENT` from
`mkdtemp`, three stages into a pipeline — after the probe, after normalize had decided what it
wanted — in a CLI whose entire error taxonomy exists so an operator never reads a trace.

Fixing it exposed the general case. `transcribe.ts` catches `NotConfiguredError` and prints
message-plus-hint at exit 2, and several commands do the same. But **`buildContext` is called
outside every one of those try blocks**, so anything raised while assembling the context — a
missing key, a bad temp dir — went straight past all of it to the top-level handler, which
prints a stack trace for whatever it does not recognise.

That handler's own comment had predicted this: an `instanceof` chain of three with a note that
a fourth case *"should become a shared marker rather than a longer condition"*. The fourth
arrived, so the marker is built. `USER_FACING` is a `Symbol.for`-keyed brand on
`NotConfiguredError`, `ProbeAbort`, `JobNotFoundError` and `JobAssetMismatchError`, and
`isUserFacing()` replaces the chain. A registered symbol rather than `instanceof` because
those four classes live in three packages, and `instanceof` fails quietly across duplicate
module instances.

`THIBI_TMP_DIR` is validated eagerly and **deliberately not created**. It is set by an
operator, so a missing directory is a typo or a volume that failed to mount — and silently
creating one inside a container turns a missing mount into a disk that fills up instead of an
error someone reads. Amendment 72.

### A cost I should not have incurred

While checking whether `NotConfiguredError` already printed cleanly, I ran the CLI with
`env -u OPENAI_API_KEY`. That does not work here: the CLI calls `loadDotEnv()`, so `.env`
put the key straight back, and instead of the configuration error I was testing, a real
16.6-minute transcription went to OpenAI. **$0.0998**, nothing persisted (`--no-db`, output to
`/dev/null`), no useful data — the language flag was `en-US` against Burmese audio.

Recorded because the mechanism generalises: **`env -u` cannot unset what `.env` restores**,
and in this repo every CLI invocation loads `.env` from the working directory. To test a
missing-credential path, use a code path that fails before the request — a language the
provider matrix refuses — or a two-second file. Both were used afterwards, and cost nothing.

`pnpm build && pnpm typecheck && pnpm lint && pnpm test` — **921 tests across 55 files,
nothing skipped**, with Postgres, MinIO and the sidecar up. 6 are new, covering
`resolveTempRoot` including the case that must *not* happen: it does not create the directory.

Then by hand, since the defect was only ever visible by hand: a non-existent `THIBI_TMP_DIR`
now exits **2** with a copyable `mkdir -p`, a path that is a file exits 2 saying so, and both
fail before the probe rather than after normalize.

loud refusal beat a plausible wrong number, which is the whole thesis of the phase.

## Publishing it — and the four defects that surfaced on the way

Executed against [`plans/phase-05-eval-harness.md`](../plans/phase-05-eval-harness.md) §5.8,
§5.9 and §5.11. Four commits. The harness could measure and had nowhere to put the answer:
`packages/languages` could not import a tier, `/settings/languages` had nothing to render, and
the only record of the first CER was a table printed to a terminal.

### The seam first, and it was worth doing first

The previous sitting left `runner.ts` untested and said so. Taking the seam — `loadTsv` and
`fetchClips` as `RunAsrDeps` fields defaulting to the live implementations — took twenty
minutes and immediately found something the plan had specified correctly and the code had
not.

**`--budget-usd` was not a budget.** It tested `spent >= budget` *before* each call, which
permits the call that crosses the ceiling and refuses only the next one. A $0.03 ceiling with
$0.02 clips ran two clips and spent $0.04, and the overshoot is unbounded in principle: one
expensive clip can cross any ceiling by any amount, and the run then reports the limit as
enforced. §5.8's own words — "checks *before* each billable call" — were the specification it
failed. It now projects the clip's cost from `numSamples / 16000` and the run's rate. Where no
rate is known the projection is zero and it degrades to the old test, one clip late, and a
test asserts that weaker behaviour rather than letting it look exact. Amendment 75.

The other find was smaller and the same shape: a language the budget cut off reported
`not run` while having scored clips. It says `stopped part-way` now, and those clips are still
discarded — a CER over however many clips the money reached is not a measurement, and in a
table it is indistinguishable from a complete one.

### The runlog recomputes, and that is the point

`results/runs/<runId>.jsonl` is written as work completes, so a crashed run is still
analysable. The property that earns it its place is the second one: `thibi eval report --run`
re-derives both outputs with the network off, so arguing about a threshold costs nothing.

That only holds if the reader **recomputes**. `score` lines carry per-clip edit counts rather
than rates — the corpus estimator is the ratio of sums and the bootstrap resamples the pairs,
so rates could reproduce neither the headline nor its interval — and the reader recomputes the
CER, the interval and the tier from them. A reader that trusted the stored `cer` would
reproduce the old report perfectly and go on reproducing it after somebody changed the
estimator, which is the one thing the file exists to prevent. Proved by rewriting a stored
`cer` to 0.999 in a log and watching the replay ignore it.

Writing it forced one design change and caught one trap. The run id had been minted *inside*
`runAsrEval`, so the caller could not name the log file until the run it was supposed to be
recording had finished; it is a caller-supplied option now. And the first reader recomputed
from the `score` lines of a budget-stopped language — resurrecting exactly the partial CER the
runner deliberately drops.

### Two defects the sweep found by being regular

**Every FLEURS dev split measured is single-gender in its entirety.** Not the sample — the
split. `my_mm` 384 FEMALE, `ha_ng` 296 FEMALE, `yo_ng` 378 MALE, `jv_id` 295 MALE. Amendment
68 recorded this for Burmese and it read as a quirk of one config; it is the shape of the
dataset, so risk 2's mitigation — "report the gender split" — reports a constant for every
language and the concentration it was meant to surface stays invisible across the whole eval
set. `distinctIds` is the column doing that work instead, and it earned its place immediately:
`ha-NG`'s thirty clips cover 28 sentences, `jv-ID`'s cover 27. Amendment 76.

**The cost was wrong, and the tell was that it was too regular.** All four languages billed
exactly $0.0365 despite visibly different total audio, and every one of 120 clips costed at
4.56 seconds. `wavDurationMs` read the data size from offset 40, which is right only for a
canonical 44-byte header — FLEURS wavs have an 18-byte `fmt `, a 4-byte `fact`, and `data` at
byte 50, so offset 40 read the same 291939 out of every file in the dataset. 291939 / 64000 =
4.56. They are 32-bit float too, so the byte-length fallback was wrong by 2× as well.

Blast radius, stated rather than assumed: `durationMs` feeds `usage.audioMs` and a segment-end
fallback and never touches the transcript, so the CERs above stand; `tiers.json` carries no
cost field, so no published artefact is wrong. What is wrong is the recorded spend — $0.146
against a real ~$0.49 — and correcting it means paying for the sweep twice, so it stands with
a note against it. Amendment 77. The general shape is worth keeping: **a wrong number derived
from real bytes, identical across every input and plausible in magnitude, is the hardest kind
to see. Regularity was the only signal.**

## Risk 10: merging `tiers.json` without letting it lie

Executed against [`plans/phase-05-eval-harness.md`](../plans/phase-05-eval-harness.md) risk 10,
raised by the previous sitting and closed by this one. One commit.

The defect: `buildTiersFile` emitted a row per language *in the current run*, so publishing a
five-language sweep after a hundred-language one left five rows and dropped ninety-five — from
the file `packages/languages` compiles at build time. Silent, total, and a completely ordinary
thing to do by accident.

**The objection to merging was correct and is what shaped the fix.** Rows from several runs
under one run's header is a document that lies in a different way: `sampling`, `baseline` and
`runId` all describe one measurement, and a merged file would attach them to rows they had
nothing to do with. So v2 stops merging *rows* and separates the layers instead:

| key | what it is | on publish |
|---|---|---|
| `runs` | per-run context — provider, model, split, `n`, baseline | accumulated |
| `measurements` | one per `code\|provider\|model` — the evidence | accumulated, newest wins per key |
| `languages` | one row per language — the claim | **derived, never merged** |

Deriving rather than merging the claim is the part worth keeping: `languages` is a pure
function of `measurements`, so it cannot drift from the evidence, and republishing an
untouched file is a no-op. `deriveLanguages` is asserted to be idempotent for that reason.

### The trapdoor merging opens

Once measurements accumulate across runs, they accumulate across *providers* — and this
project deliberately measures `my-MM` on Groq, because reproducing that failure on demand is
worth a flag. A naive merge would have published Groq's romanized non-words as Burmese's
tier and marked the product's best language unsupported.

So the rule: **a measurement only sets a tier if it came from the provider `chooseProvider`
would actually use for that language.** The rejected measurement is kept — in `measurements`
and on the row's `otherProviders` — because "Groq is unusable for Burmese" is a finding worth
having. It is simply not a fact about Burmese. And a language whose chosen provider has never
been measured reads `not-run` however many others have, because a CER from a provider we
would not route to says nothing about what a user would receive.

Anchoring on `chooseProvider` turned up a matching staleness in that function: it returned
`language.seed.tier`, so the picker reported a seeded guess while `resolveLanguage` reported a
measurement — two answers to one question, in one package, differing exactly when a
measurement existed. It reads the measured tier now, with the same `hasMeasurement` guard the
registry uses.

### Two smaller corrections

**The tier is recomputed at derive time**, by `assignTier`, rather than read back off the
stored measurement — so a stored tier and the numbers under it cannot disagree, and applying a
human sign-off is one more input to the same decision instead of a manual promotion. It paid
for itself immediately by catching a test fixture that asserted
`blockedFromVerifiedBy: ['humanReview']` over an interval whose own `ciHiRatio` was 1.167.

**`baselineSuspect` compares against the last run with the same provider and model**, not
simply the last run. Otherwise every provider switch trips the alarm — which is not drift, and
an alarm that cries wolf on a routine action stops being read.

## Two checks before widening the sweep

Executed against [`plans/phase-05-eval-harness.md`](../plans/phase-05-eval-harness.md) risk 2
and the `yo-NG` caveat this sitting's earlier handoff note left. One commit, $0.2394 spent.

### Yoruba, and a wrong guess caught

The handoff note flagged `yo-NG` at 0.305 as "measured once, check `letterlikePunct` before
repeating it". That guess was wrong and could not have been right: Yoruba's tone marks are
combining marks and `stripPunct` never touches them. Recorded because it was a reasonable
guess that got as far as a handoff document.

Re-scoring the committed runlog costs nothing, and the answer was in the raw hypotheses. The
three worst clips are plain ASCII — *"Awon olopa sope, o dabi enipe oro naa ti wa nibe"* —
while the best carries full diacritics. Quantified by stripping tone marks and folding the
sub-dot letters on both sides:

| | |
|---|---|
| CER as measured | 0.261 (reproduces the published `cer` exactly) |
| CER ignoring diacritics | **0.065** |
| hypotheses with no tone marks at all | **10 / 30** |
| references with tone marks | 27 / 30 |

Google recognises Yoruba *words* about as well as it does Burmese (0.064) and Hausa (0.059),
and fails at diacritization — completely on a third of clips, inconsistently on the rest. The
tier stays `experimental` and should, because tone is lexical in Yoruba and undiacritized
output is wrong rather than untidy. But the failure is a different one from what 0.305
implies, and it is the kind a Phase 6 prompt could address where a word-error problem would
not be. Amendment 80.

### Tar order versus id-seeded

Risk 2 has asked since the phase was written whether tar-order sampling quietly selects
something. `--sample-strategy id-seeded` is now built as specified — pull `--oversample × n`,
dedupe by sentence id, seeded-shuffle, take n — and measured against tar order at n=30:

| | tar-order | id-seeded | |
|---|---|---|---|
| `my-MM` | 0.064 [0.047, 0.080] | 0.084 [0.059, 0.107] | **+31%** |
| `ha-NG` | 0.059 [0.043, 0.076] | 0.056 [0.046, 0.067] | −5% |
| `yo-NG` | 0.305 [0.249, 0.362] | 0.319 [0.267, 0.368] | +5% |

Every interval overlaps, so the answer to the question as asked is **no, not measurably**.

The finding is next to it. `my-MM` is the denominator of every ratio in the file, so its 31%
move took `ha-NG` from 0.91 to 0.67 and `yo-NG` from 4.75 to 3.80 **without either language
changing**. At n=30 the ratio a tier threshold reads is noisier than the CER it derives from,
and it is noisy in a way that moves every language at once. Whether the thresholds should
widen at small n, or the baseline should simply be measured at a larger n than everything it
calibrates, is now the open question in risk 2's place.

`distinctIds` came back 30/30 for all three under id-seeded, against 28 and 27 under tar
order — the dedupe doing exactly what amendment 68 asked for.

### And the alarm that cried wolf

Switching strategy **tripped the baseline-drift guard** and blocked the publish, warning about
a baseline that had not drifted at all. That is the second false positive from that check
after comparing a Groq baseline with a Google one, so a comparable baseline now requires the
same provider, model, split, `n` *and* strategy. The cost is stated rather than hidden: change
`--n` or the strategy and the guard is silent for that run, because there is no previous
measurement of the same thing to compare against.

One decision worth writing down because the opposite looked obviously right for a minute: the
sampling strategy is **not** in the response-cache key. The cache answers "what did this
provider say about this clip", the key already carries `clipHash`, and adding the strategy
would split the cache and re-bill every clip the two strategies share — which on a wide prefix
is most of them.
