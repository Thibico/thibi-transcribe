## The prompts, because there was nothing to import

[`1b5152c`](https://github.com/Thibico/thibi-transcribe/commit/1b5152c) —
*Build the prompts the eval harness has to measure*

§5.10's second guarantee is that `packages/eval` imports the **real** `buildCleanupPrompt`
from the engine and never holds a prompt string of its own, because a copy drifts within a
month and the gate then measures text nobody ships. `packages/engine/src/llm/` did not exist,
so the eval could not start without it.

Three prompt ids now do: `cleanup.current`, `cleanup.restraint` and `translate.default`. The
first is the prompt running in production today with the language taken out of it, and it is
here to be *measured*, not used — it keeps both lines phase-06 says must never ship again,
because §6.5 step 4 requires the old prompt to still fail the gate and a regression test with
no regression in it is decoration.

**Two registry fields the plan's own mapping table names do not exist.** §6.4 reads
`script.hasCase` and `text.punctuation.clause`; the registry has neither, and one of them
cannot be derived from Unicode. Georgian Mtavruli capitals carry the `Lu` category, so a
derivation from character properties would say Georgian has case and the cleanup prompt would
instruct a model to capitalise Georgian sentences, which standard Mkhedruli orthography does
not do. Both are now hand judgements in `gen-scripts.ts` beside the other script-level ones.

The clause field exists because `text.punctuation.sentenceEnders` is a single flat list that
several languages fill with both kinds of mark — **Burmese lists `၊` beside `။`, Amharic `፣`
beside `።`** — so a prompt offering that list as "sentence-ending punctuation" tells a model
the Burmese comma ends a sentence. `promptVars` subtracts one set from the other, once, rather
than in 116 language rows. Empty means *not recorded*, not "this script has none", and an
empty set omits the permission line entirely: the prompt is a list of what may be changed, so
an unlisted mark is one the model may not insert.

**The version guard is a digest file rather than a snapshot, and that is the point.** A
snapshot test fails on any change and is fixed by running `vitest -u`, which is exactly how a
prompt edit ships with a stale `promptVersion` — and the Phase 5 cache keys on
`promptId` + `promptVersion`, so a stale version makes a bumped prompt a cache *hit* and the
gate passes on the previous prompt's numbers. `prompt-versions.json` records the version and a
sha256 over the six rendered snapshots, and both halves are asserted.

## The harness

[`d49e58b`](https://github.com/Thibico/thibi-transcribe/commit/d49e58b) —
*Measure a cleanup prompt against doing nothing*

`packages/eval/src/llm/`: four metrics, two runners, a response parser, a ledger and the gate.

`content_delta` is the one worth restating. It is a **contract check, not a quality score**:
both sides stripped of punctuation, case and whitespace, so a compliant pass leaves them
identical and any non-zero value is a rewrite by definition, with no argument available about
whether the rewrite was an improvement. Whitespace is forced off regardless of the language
profile, because the prompt is *permitted* to change spacing and leaving it in would report
every legitimate space insertion as a rewrite.

`control` is an arm rather than a constant, it costs nothing, and it runs first — so a budget
that runs out mid-run still leaves the column every other arm is judged against. The gate's
pass condition is beating it per language, not clearing a threshold: thresholds get tuned
until they pass, and a control cannot be.

The translation eval measures its own two controls rather than quoting the research's 87.0
ceiling and 65.6 bar. Both are added to every run the way the ASR runner adds its baseline.

## What the first real run found

[`db8ccab`](https://github.com/Thibico/thibi-transcribe/commit/db8ccab) —
*Give the cleanup and translation evals a command, and fix what the first real run found*

Two segments of Hausa against `openai/gpt-oss-20b` on Groq, and a defect 41 tests had not
found. §5.10's entity regex is `\d[\d.,:/٫٬]*`, greedy over its separator class — so a
compliant pass adding a full stop turned `…kasa a 1755` into `…kasa a 1755.`, `1755` left the
multiset and `1755.` joined it: **entity_drift 2.0 against a 0.02 gate**. Every arm in every
language would have failed the gate for making the one edit the prompt exists to make.

The same two segments are also the first evidence the metrics see what they were built to see.
`casa branca` came back as `casa blanca` — a proper name rewritten in a language the model
half-knows — and `entity_drift` is blind to it, both tokens being in-script and lowercase.
`content_delta` caught it at 0.0049, which is *below* the 0.005 gate.

## The failure that mattered

[`c783483`](https://github.com/Thibico/thibi-transcribe/commit/c783483) —
*Make the gate fail when it measured nothing, and wait out a rate limit*

The first six-language run asked for six languages and measured **none**. Five were lost to a
single Groq 429 apiece and one to a `json_validate_failed` 400, because a call error
propagated out of the per-language loop. The gate then printed

```
gate: pass — every arm is at or below its control.
```

and exited 0, having skipped every language it had nothing to compare.

That is this project's own stated failure mode, arrived at from the inside: **a check that
cannot distinguish "clean" from "did not run" is not a check.** Three fixes — a failed call
costs its segment and not its language; a language the run asked for and did not measure is a
gate *failure* rather than a skip; and a run that measured nothing exits non-zero with or
without `--gate`. Plus the retry ladder the engine already had, honouring the wait Groq states
in its 429 body: rate limits are not exceptional here, since the on-demand tier caps at 8000
tokens a minute and one segment costs about 2000.

## What it measured

Six languages, `openai/gpt-oss-20b` on Groq, n=10, `cer_punct` against a do-nothing control:

| code | control | current | restraint | content_delta (current → restraint) |
|---|---|---|---|---|
| `my-MM` | **0.016** | 0.021 | **0.027** | 0.0024 → 0.0000 |
| `yo-NG` | 0.032 | **0.096** | 0.018 | **0.0952** → 0.0011 |
| `ps-AF` | 0.017 | 0.030 | 0.014 | 0.0064 → 0.0000 |
| `so-SO` | 0.043 | 0.044 | 0.030 | 0.0239 → 0.0021 |
| `ha-NG` | 0.036 | 0.028 | 0.022 | 0.0094 → 0.0009 |
| `xh-ZA` | 0.042 | 0.051 | 0.029 | 0.0201 → 0.0051 |

**The research direction reproduces and the restraint prompt reverses it.** The shipped prompt
is worse than doing nothing in five of six languages, and the replacement beats the control in
five of six. `content_delta` is the clearer signal, because it has no argument attached: the
shipped prompt rewrote **9.5% of Yoruba's characters**, 2.4% of Somali's and 2.0% of Xhosa's,
while the restraint prompt sits at or near zero everywhere. Magnitudes differ from the research
table — different model, n=10 not 10-of-a-different-set — and the ordering is what was worth
checking.

**Burmese fails, exactly where [phase-06](../plans/phase-06-llm-passes.md) risk 1 said it
would.** Restraint 0.027 against a 0.016 control, further above it than the research's own
0.019. The run says what it is doing wrong: it inserts `၊` at every phrase boundary, so
`ဖြစ်သူ ဂျမီစီမင်အော့ဖ် သည်` comes back as `ဖြစ်သူ ဂျမီစီမင်အော့ဖ်၊ သည်` — a clause mark where
the reference has a space. Its `content_delta` is **0.0000**: the contract held perfectly, and
the punctuation it was licensed to choose was the wrong punctuation. That is a prompt problem
with a clear shape, and it is Phase 6's to close. The gate is not being relaxed for it.

The gate exits 2 with twelve failing conditions, which is the right answer for a run containing
an arm designed to fail. With `--arms control,restraint` two would remain: Burmese on CER, and
Xhosa on `content_delta` at 0.0051 against a 0.0050 tolerance.

**One methodological gap the run exposed and this session did not close.** Groq returns HTTP
400 `json_validate_failed` on a minority of calls, more often on Burmese and Yoruba than on
Latin-script languages, so `yo-NG current` was scored over the 7 segments that came back while
its control was scored over all 10 — and the three that failed are not a random three. Every
arm of a language should be scored over the intersection of what all arms returned. Recorded in
the handoff note rather than fixed, because fixing it changes numbers and this run is the first
evidence there is.

## One loose end worth naming

Some of the Groq 400s explain themselves in the response body:

# Third sitting — switching the gate on, and switching it off again

## It did not parse

The workflow written earlier in the day used `if: ${{ !secrets.GROQ_API_KEY }}` for its
"no key, fail loudly" step. The `secrets` context is not available in an `if` expression, and
GitHub rejects the **entire file** with `Unrecognized named-value: 'secrets'` rather than the
step — so for a day the repository contained a file that looked like a quality gate and was
not one. It could not have been caught by review and nothing in `pnpm test` reads CI
configuration; it surfaced the first time somebody tried to dispatch it. **A CI file is not
verified by review, only by a run.**

Fixed by mapping the secret to a job-level `env`, which *is* available in `if`.

## Then it ran for three hours

With the secret set and the file valid, a six-language n=10 dispatch — 120 calls — passed three
hours on a GitHub runner without finishing. Probing the provider directly while it was stuck
ruled out the obvious explanation: the account was healthy, 999/1000 requests and 7923/8000
tokens available, and a test call returned instantly.

Two real defects came out of that probe, and neither could have been found by reading the code:

**`openai/gpt-oss-20b` is a reasoning model.** Its responses carry
`completion_tokens_details.reasoning_tokens`, and nothing capped them, so it spent an unbounded
number of tokens thinking before writing the JSON. That is latency on every call, it drains the
per-minute token bucket the whole run is throttled by, and it is the provider's own stated
cause of a share of the previous sitting's failures — `failed_generation: "max completion
tokens reached before generating a valid document"`. Now capped at 4000.

**`withRetry` honours `Retry-After` with no ceiling.** Right for a window measured in seconds,
dangerous for one measured in hours: a 429 reporting a 40-minute reset becomes a 40-minute
sleep, three times over, and **from outside the process a sleep is indistinguishable from a
hang** — no output, no progress, no error, and a job GitHub kills at six hours having measured
nothing. Waits over a minute are now dropped rather than obeyed, so the retry budget is spent
in under two minutes and the segment fails with the provider's own message attached.

Whether the uncapped wait is what actually stalled *this* run is unproven — GitHub does not
serve a job's logs until it ends, and the run was cancelled before that mattered. It is a
defect either way, and it is precisely the defect that would hide the real cause.

## And then it was parked

The user's call, and the right one: measurement had taken a full sitting and the product still
has no UI. The `pull_request` trigger is commented out with the reasoning in the file header,
`workflow_dispatch` still works, and `thibi eval cleanup --gate` is run by hand before a prompt
change ships — which is step 4 of [phase-06](../plans/phase-06-llm-passes.md) §6.5 and always
was. Step 6, the CI half, is what is parked.

**What is not parked, and this is the part worth being clear about.** `ci.yml` runs `pnpm test`
on every push, and the metrics parity fixture, the prompt snapshots and the **prompt version
guard** all live there. A prompt edited without a `promptVersion` bump still fails CI for free.
Only the part that spends money — measuring an edited prompt against a live model — waits.

### The day-one checks the plan says to settle

Four, and none of them blocked anything.

**pg-boss is at v12, not the v10 the plan's risk 1 assumes.** Risk 1 is about version churn —
v10 made queues first-class objects and changed `work()`'s signature from v9 — so being two
majors further along is exactly the risk materialising before a line was written. It cost
nothing because the plan's own mitigation was to define a `Doorbell` interface up front, which
is what happened; nothing outside a not-yet-written adapter will import pg-boss.

**A dedicated client is available.** Risk 3 warns that the advisory-lock slot layer degrades
silently to no limiting at all if `ctx.db` cannot hand out a client that stays put for a
step's duration. `Db` is a Drizzle handle over a `pg.Pool` exposed as `$client`, so
`$client.connect()` gives one. Not needed yet; checked because discovering otherwise later
would have been a retrofit.

**`runs.state` already includes `partial` and `cancel_requested_at` already exists** — Phase 1
put them in migration 0000. The plan lists both as modifications; they are not.
`cancel_requested_by`, which §10's `requestCancel` writes, does *not* exist and will need one.

**Postgres is direct, not pooled.** No PgBouncer in the dev Compose file, so `LISTEN` works.

### The tables

`run_steps`, `run_events`, `rate_buckets`, and `segments.placeholder_reason`, as migration
0004. Two decisions went against the plan's DDL and both are about which convention wins.

`step_state` is a real Postgres enum where every other state column in this schema is `text`
with a Drizzle `enum` option — which is a TypeScript constraint and nothing more; the column is
plain text and the database will accept any string at all. That is fine for `runs.state`, which
only ever moves through Drizzle. `run_steps` is the one table most of whose writes are
hand-written SQL: the planner inserts through `jsonb_to_recordset`, the recovery sweep is an
`UPDATE … CASE`, the reconciler casts. None of those paths sees a TypeScript type, so a typo'd
state would be stored and then match no predicate — a step that is neither live nor terminal,
invisible to the reconciler and to `/admin/queue` alike. Adding a state is now a migration,
which is the right price for a column whose whole job is to be exhaustively matched. `kind`
stays `text` for the mirror-image reason: kinds are dispatched through a registry keyed by
string, so adding one should be a code change.

`cost_usd` went the other way — `double precision`, not the plan's `numeric(12,6)`, matching
`runs.cost_usd` and `usage_records.usd`. A step's cost sums into a run's, and a sum mixing
`numeric` with `double precision` returns `double precision` anyway, so the stricter type buys
nothing here and costs consistency with every other money column.

Recorded as [amendment 89](../plans/00-overview.md).

### The correction that matters: `partial` could not happen

Phase 9 §9 exists to make one claim true — *a three-hour transcript with one bad 55-second
chunk is still valuable, and losing it is what makes people stop trusting the tool*. The
reconciler as specified could not produce that outcome, for two independent reasons, and
writing the test is what surfaced both.

`asr.chunk` is not `optional`. So §3's `hardFailed` predicate —
`!s.optional && (failed || dead)` — is true the instant one shard dies, and the terminal branch
tests `hardFailed` before it tests `partial`. The `partial` branch was dead code.

Fix that, and it still cannot happen, because §3's dependency-poisoning rule marks
`normalize.text` — which depends on `['asr.chunk','*']` — `failed` the moment any dependency is
`dead`. The seven survivors would never have been assembled into anything.

Both close with one rule rather than two patches. A `dead` step of a **casualty kind** both
satisfies its dependents and does not count toward `hardFailed`, **provided a sibling shard of
that kind succeeded**. The proviso is the whole honesty of it: if none succeeded, nothing was
transcribed, there is no partial transcript to hand anyone, and the run has genuinely failed —
which is why the all-chunks-dead case still lands on `failed` and has its own test. What makes
proceeding over a casualty safe at all is the placeholder segment: the timeline stays
contiguous, so subtitle reflow, export, the editor's virtualiser and speaker reconciliation
each see the shape they already expect rather than a hole each would need a special case for.

Emptying `CASUALTY_KINDS` fails the partial test and leaves the all-dead one passing, which is
how the rule was confirmed to be doing work rather than describing it.
[Amendment 86](../plans/00-overview.md).

### Three smaller ones, each of which would have shipped silently

**A queue nothing subscribes to.** §2's step-kind table routes `normalize.text` and
`reconcile.speakers` to a queue called `worker`. §6's queue table, its `SUBSCRIPTIONS` map and
the default `WORKER_QUEUES` all omit it. Every run would have planned two steps onto a queue no
container listens to; they would sit `ready` forever, the queue would report depth 0, and the
run would never finish — which is the precise misconfiguration §12 tells an operator to watch
for, written into the plan that warns about it. `queues.test.ts` now asserts that some
container subscribes to every queue that exists, which is the assertion that would have caught
it.

**A non-deterministic aggregate.** §4's materialise SQL uses `array_agg(dep.id)` with no
`ORDER BY`, so Postgres may aggregate a wildcard's eight matches in any order. Replanning an
unchanged run then rewrites `depends_on` with the same uuids in a new sequence,
`IS DISTINCT FROM` stops suppressing the update, and planning stops being a no-op. The plan's
own test — "`depends_on` arrays are byte-identical across both calls" — would fail
*intermittently*, which is the worst way for a test to fail because it passes on most runs.
Removing the `ORDER BY` fails it 3 runs out of 3, which is how it was confirmed rather than
argued. The idempotence tests assert on `xmin` rather than on column values, because `xmin`
advances on any UPDATE including one that writes exactly what was already there — comparing
columns alone would pass while the second call rewrote all twenty rows.

**A test asserting the opposite of the design.** §-Tests says twenty parallel `reconcile` calls
produce "exactly one send per step". They do not, and must not: §3 deliberately re-rings
anything already `ready` on every pass, because that is what covers the window between COMMIT
and `sendStep`. Several sends is the design. The property that actually prevents a double
execution is that they all carry the **same singleton key**, and that is what is asserted now.
[Amendment 87](../plans/00-overview.md).

### Two retry tables that had already drifted

`packages/engine/src/retry.ts` capped `asr.chunk` backoff at 30 s and `diarize` at 60 s. Phase
9 §5's table says 120 s and 300 s. Neither number came from a measurement: the overview
specifies attempts and base delay per kind and never specified a cap, so each file invented one
and nothing ever compared them. There is one table now — `queue/retry.ts`'s `POLICY` — and the
in-process one derives from it under a test. That makes "which one is right?" unaskable rather
than merely answerable, which is the only durable form of the fix.

Widening `isRetryable` while there closed a real gap rather than a stylistic one. **Node and
undici report connection failures on `err.code`, not in the message.** The old predicate
regex-matched `err.message` only, so every `UND_ERR_CONNECT_TIMEOUT` and
`UND_ERR_HEADERS_TIMEOUT` — which is to say every connect and headers timeout from `fetch`, the
most common transient failure this project actually sees — was classified as permanent and
never retried. Also added: 408 and 425 beside 429 and 5xx, and the negative rule that matters
more, that a 4xx from a provider is a configuration or payload error whose retry cannot
succeed, burns quota, and delays the operator seeing the real message by the length of the
backoff.

Phase 9's `CancelledError` is the existing `AbortedError` and there is deliberately not a
second class. [Amendment 88](../plans/00-overview.md).
