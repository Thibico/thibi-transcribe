# Phase 4 — Whisper providers

## Goal

At the end of this phase three more providers sit behind the same `TranscriptionProvider`
interface: OpenAI and Groq over a shared `whisper-http.ts` transport, and self-hosted
faster-whisper over the Phase 3 sidecar — one image, two models, one shared `hf-cache`. They exist
for two reasons and it is worth being blunt about both. First, faster-whisper is the only provider
in the system with **genuine per-word confidence**, which is what makes the low-confidence QA
surface real rather than decorative. Second, and mostly, **the harness needs comparators**: the
product thesis is that for the 44 exclusive-language set Whisper either refuses the code or mangles
it, and Phase 5 cannot demonstrate that without the code paths to measure. These providers are
built to be measured, not to be recommended.

## Design

### 1. `whisper-http.ts` — the shared base

OpenAI and Groq speak an identical request shape, so there is one transport and two thin
configuration modules over it.

```ts
export interface WhisperHttpConfig {
  baseUrl: string;      // https://api.openai.com/v1  |  https://api.groq.com/openai/v1
  apiKey: string;
  model: string;
  organization?: string;
}
export interface WhisperHttpLimits {
  syncMaxBytes: number;         // 25 MB both, today
  syncMaxSeconds: number;
  maxConcurrentRequests: number;
  rpm: number;                  // a setting, not a constant — it is tier-dependent
}
```

`POST {baseUrl}/audio/transcriptions`, `multipart/form-data`:

| Field | Value |
|---|---|
| `file` | the chunk, 16 kHz mono FLAC |
| `model` | `whisper-1` · `whisper-large-v3` · `whisper-large-v3-turbo` · `gpt-4o-transcribe` |
| `language` | **ISO-639-1 base code** (`my`), not the BCP-47 locale (`my-MM`) |
| `response_format` | `verbose_json` |
| `timestamp_granularities[]` | `word` |
| `timestamp_granularities[]` | `segment` |
| `prompt` | glossary terms, ≤224 tokens (§4) |
| `temperature` | `0` |

Three traps worth writing down because each costs an afternoon:

- `timestamp_granularities[]` must be sent as a **repeated form field with the literal brackets in
  the field name**, and it is honoured only with `response_format=verbose_json`. Asking for `word`
  without `segment` still returns segments; asking for neither returns segment-level only.
- The API takes `my`, not `my-MM`. The registry exposes `iso639_1`, and the adapter maps
  BCP-47 → 639-1 and **fails loudly** when a language has no 639-1 code. That alone excludes `ceb`,
  `nso`, `luo`, `kea`, `umb` — consistent with the probe, which found every Whisper endpoint
  rejecting them.
- `verbose_json` is not supported by the `gpt-4o-*` transcribe models at all. See §2.

Response:

```json
{ "task": "transcribe", "language": "burmese", "duration": 58.6, "text": "…",
  "segments": [ { "id": 0, "seek": 0, "start": 0.0, "end": 4.2, "text": " …",
                  "tokens": [...], "temperature": 0.0, "avg_logprob": -0.31,
                  "compression_ratio": 1.6, "no_speech_prob": 0.02 } ],
  "words": [ { "word": "…", "start": 0.0, "end": 0.34 } ] }
```

**`words` is a flat top-level array, not nested inside segments.** This is the biggest structural
difference from Google and the likeliest place for an off-by-one, so it gets its own module:

```ts
// providers/whisper/attach-words.ts
export function attachWords(
  segments: WhisperSegment[], words: WhisperWord[], epsMs = 20
): { segments: ProviderSegment[]; unattached: number }
```

Containment by start time with a 20 ms tolerance: a word belongs to the first segment where
`w.startMs >= s.startMs - eps && w.startMs < s.endMs + eps`. Leftovers are counted, reported in
`TranscribeResult.usage.wordsUnattached`, and logged — never silently dropped.

Parsing rules:

```ts
segment.confidence = clamp01(Math.exp(seg.avg_logprob));   // segment level only
word.confidence    = undefined;                             // never fabricated
result.wordTimingQuality = words.length > 0 ? 'full' : 'none';
```

Hallucination guard: drop segments where `no_speech_prob > 0.6 && text.trim().length < 3` — the
"Thank you." that Whisper emits over trailing silence. Count them and log the count; if more than
10% of segments are dropped, surface it as a run warning rather than quietly deleting a tenth of
the transcript.

Retry: `429` honours `Retry-After` exactly; `5xx` gets full-jitter 5 × 2 s from `util/retry.ts`;
`400` is never retried. Groq returns `x-ratelimit-remaining-*` headers — record them in
`run_steps.output` now so Phase 9's token bucket has data to work with, but do not build the bucket
here.

### 2. OpenAI specifics

| Model | Word ts | Segment ts | Codes accepted | Note |
|---|---|---|---|---|
| `whisper-1` | yes | yes | **57** | the only timestamped path |
| `gpt-4o-transcribe` | **no** | no | **67** | no `verbose_json`; `json` / `text` only |
| `gpt-4o-mini-transcribe` | **no** | no | 67 | ditto |

The 57 vs 67 numbers are the probe's, not the docs'. `gpt-4o-transcribe` adds
`bn fil gu ka ml nb te yue zh-CN zh-TW`.

```ts
resolveModel(code: string, { requireWordTimestamps }: ResolveOpts): string | null {
  const m = matrix.openai[code];
  if (!m?.supported) return null;
  if (requireWordTimestamps) {
    return m.models.includes('whisper-1') ? 'whisper-1' : null;   // ← the gpt-4o case
  }
  return m.models.includes('gpt-4o-transcribe') ? 'gpt-4o-transcribe' : 'whisper-1';
}
```

So `resolveModel('bn-IN', { requireWordTimestamps: true })` returns `null`, because Bengali is
`gpt-4o-transcribe`-only and that model returns no timestamps. A bare `null` is how this gets
misdiagnosed as "OpenAI doesn't do Bengali", so the CLI must always print the reason:

```
OpenAI supports bn only on gpt-4o-transcribe, which returns no timestamps.
Use --no-word-timestamps, or pick another provider (google: chirp_2, verified).
```

Capability:

```ts
capabilities: {
  modes: ['sync'],
  wordTimestamps: true,          // whisper-1
  wordConfidence: false,         // ← deliberate
  segmentConfidence: true,
  diarization: 'none',
  adaptation: 'prompt',
  languageDetection: true,
  limits: { syncMaxBytes: 25 * 1024 * 1024, syncMaxSeconds: 600,
            maxConcurrentRequests: 4, rpm: 500 },
  staging: 'none',
}
```

**No true confidence, and we do not pretend otherwise.** `exp(avg_logprob)` is a
length-normalised model likelihood — roughly monotone with quality, entirely uncalibrated. It is
fine for sorting segments by suspicion and useless as a probability. Mapping it at *segment* level
and setting `wordConfidence: false` is the whole policy. Concretely: the low-confidence dotted
underline in the editor reads `words.confidence`, so for OpenAI and Groq runs it simply does not
appear, and the toolbar says *"per-word confidence is not available from this provider"* rather
than showing an empty count. Implying precision that is not there is worse than showing nothing.

Limits arithmetic: ~~25 MB at 16 kHz mono FLAC (~110 KB/s) is about 230 s, so the byte budget
binds long before `syncMaxSeconds`.~~

**Corrected 2026-08-10 — the constant was about 6× too high and it inverts the conclusion.**
Measured on the first real normalized derivative Phase 2 produced: **18.9 KB/s**, i.e. 22.7 MB
for 1200 s of 16 kHz mono FLAC, a 59% ratio against raw 16-bit. At that rate OpenAI's 25 MB cap
binds at about **1320 s — 22 minutes**, not 230 s.

So the byte budget does **not** bind first for these providers, and a chunk here can be an order
of magnitude longer than the plan assumed. What binds instead has to be established rather than
inherited from this paragraph: OpenAI publishes no separate duration limit, so the practical
ceiling is request timeout and the cost of losing a long chunk to one failure. Pick a duration
budget deliberately — the seam merge means more chunks is not free either, at ~2–3 words lost per
hard cut before de-duplication — and record the reasoning where the constant lives.

Two caveats on the 18.9 KB/s. It is one clip of Burmese news speech, and FLAC is content-dependent:
denser material will exceed it. And it is only true *since* 2026-08-10, because until then the
`norm_16k_mono_flac` recipe emitted 192 kHz — `loudnorm` resamples internally and the
`aresample=16000` in front of it was silently discarded — which produced 113 KB/s and is very
close to the number this paragraph originally carried. Re-measure across the Phase 5 eval corpus
before treating 18.9 as settled; the bitrate-derived budget at `lib/audio/chunk.ts:134-136` is
still the right *mechanism*, and it derives the budget from the actual file rather than from a
constant, which is why it survives the constant being wrong.

### 3. Groq specifics

| Model | Note |
|---|---|
| `whisper-large-v3` | accepts ~100 codes — essentially the whole tokenizer, no docs gate |
| `whisper-large-v3-turbo` | faster, materially worse on low-resource languages |
| `distil-whisper-large-v3-en` | English only |

From `research/language-support-whisper-vs-google.md:86-97`, on the same 12-second clip:

| Call | Output |
|---|---|
| Google `chirp_2` | `အာဆီယံ ရဲ့ ဆုံးဖြတ်ချက် ကို နေပြည်တော် က တုံ့ပြန်ခဲ့ ပါ တယ်` — correct |
| Groq, `language=my` | `လာက္းကေက် ရိုရ်းသဲ့ထါတ် နို့ရ်းတို့အ်းတ်` — Myanmar-script non-words |
| Groq, autodetect | `ASEAN YAK SOMPHA CHHA KOO NEPI ROKKA TONGPYAN KE BHA REUU` — romanised |

HTTP 200 all three times.

**The principle, stated once and then enforced in data: accepting a code is not support.**

`provider-matrix.json` carries per `(provider, code)`:

```json
{
  "accepted": true,
  "supported": false,
  "evidence": "measured",
  "reason": "returns Myanmar-script non-words; script integrity 0.98 but CER 0.94",
  "probedAt": "2026-07-30",
  "source": "research/language-support-whisper-vs-google.md"
}
```

`supported` is what `supportsLanguage()` returns and what `chooseProvider` reads. `accepted` exists
only so the matrix can render *"the API will take this and hand you garbage"* instead of looking
like an unprobed gap — the distinction a future maintainer needs in order not to "fix" it.

Two seeding rules, and the second is the opinionated one:

1. `supported: false, evidence: "measured"` for the Burmese case above.
2. `supported: false, evidence: "assumed"` for **every Groq code outside OpenAI's 57-language list
   that has not been through the Phase 5 harness.** Defaulting unmeasured low-resource codes to
   unsupported is the only default consistent with the overview's finding #2. Phase 5 flips them to
   `true` one at a time, each with a CER and a script-integrity number attached.

Autodetect (omitting `language`) is **disabled outright for Groq** in Phase 4 — the romanised output
above is precisely an autodetect result, and the overview already restricts autodetect to
verified+beta.

Limits: 25 MB free tier / 100 MB dev tier (a setting), `maxConcurrentRequests: 2`, and
audio-seconds-per-hour quotas tight enough that a harness sweep can exhaust them — which is a
Phase 5 budget problem, handled here only by honouring `Retry-After` and failing cleanly.

Users may still force it, because reproducing the failure on demand is genuinely useful:
`thibi transcribe --provider groq --lang my --force-unsupported` warns loudly, runs, and marks the
run `pipeline.forcedUnsupported = true`.

### 4. The glossary prompt

```ts
export function buildWhisperPrompt(
  terms: GlossaryTerm[], opts: { maxTokens?: number; languageCode: string }
): { prompt: string; included: number; dropped: number; estTokens: number }
```

- Sort by `boost` descending, then by term length descending. Join with `, `.
- Whisper's conditioning window is 224 tokens **of its own multilingual tokenizer**, and there is no
  cheap exact tokenizer in Node. Estimate conservatively — `ceil(chars / 2.5)` for non-Latin
  scripts, `ceil(chars / 4)` for Latin — and truncate at **200** estimated tokens for margin.
- Truncate from the **back**. The API silently truncates over-budget prompts from the *front*,
  which would discard the highest-boost terms — exactly backwards.
- The prompt is a style and vocabulary hint, not a constraint. Whisper ignores it freely and
  occasionally **echoes it into the transcript**. Guard: if the first segment's text begins with a
  ≥12-character prefix of the prompt, strip that prefix and count it. There is a fixture for this.
- **Do not** pass the previous chunk's tail as context on chunk 2+, the conventional trick. It
  propagates errors forward and, combined with the Phase 1 overlap LCS de-dup, doubles down on
  repetition. Glossary terms only.

The same function produces `initial_prompt` for faster-whisper, so glossary behaviour is identical
across all three Whisper providers.

### 5. faster-whisper via the sidecar

The second half of the Phase 3 image: one Dockerfile, both models, one shared `hf-cache` volume,
and **one `MAX_CONCURRENT_TASKS=1` slot shared between diarization and ASR**. State the consequence
plainly rather than letting a user discover it: a `--diarize --provider faster-whisper` run
serialises the two stages, so it takes their **sum**, not their max, and the CLI estimate must add
them. That is a deliberate protection — both workloads saturate every core and allocate GB-scale
tensors — not an oversight.

```
POST /v1/transcribe
{ "idempotency_key": "<run_step_id>",
  "audio_url": "http://minio:9000/…?X-Amz-Signature=…",
  "expected_duration_ms": 3612000,
  "language": "my",
  "model": "large-v3", "compute_type": "int8", "beam_size": 5,
  "word_timestamps": true,
  "vad_filter": true, "vad_parameters": { "min_silence_duration_ms": 500 },
  "initial_prompt": "…glossary…",
  "condition_on_previous_text": false,
  "deadline_s": 7200 }
→ 202 { "task_id" }              # same registry, same uuid5, same 429, same DELETE, same 'lost'
GET /v1/tasks/{id} → { state, progress, result: TranscribeResult }
```

Everything about the task lifecycle is Phase 3's, unchanged — that is the payoff of building the
sidecar's task API before its second workload.

```python
# services/sidecar/app/asr.py
segments, info = model.transcribe(
    path,
    language=req.language,
    beam_size=req.beam_size,
    word_timestamps=True,
    vad_filter=True,
    vad_parameters=dict(min_silence_duration_ms=req.vad_min_silence_ms),
    initial_prompt=req.initial_prompt or None,
    condition_on_previous_text=False,
)
for s in segments:                      # a generator: progress = s.end / duration
    out.append({
        "start_ms": int(s.start * 1000), "end_ms": int(s.end * 1000), "text": s.text,
        "avg_logprob": s.avg_logprob, "no_speech_prob": s.no_speech_prob,
        "words": [
            {"start_ms": int(w.start * 1000), "end_ms": int(w.end * 1000),
             "word": w.word, "probability": w.probability}
            for w in (s.words or [])
        ],
    })
```

`condition_on_previous_text=False` on purpose: the default `True` is the classic faster-whisper
repetition-loop trigger on long, low-resource audio, and long low-resource audio is the entire use
case.

**`word.probability` is a genuine per-word probability — the only one in the system.** Say so, and
surface it:

```ts
capabilities: {
  modes: ['sync'],               // 'sync' from the engine's view; async at the transport
  wordTimestamps: true,
  wordConfidence: true,          // ← the only provider that can claim this
  segmentConfidence: true,
  diarization: 'none',
  adaptation: 'prompt',
  languageDetection: true,
  limits: { syncMaxBytes: Infinity, syncMaxSeconds: Infinity, maxConcurrentRequests: 1, rpm: 0 },
  staging: 'none',
}
```

Consequences that must be visible in the product, not just the type: the low-confidence dotted
underline, the *"38 uncertain words"* toolbar count and the `words.confidence < 0.5` index are
fully live for faster-whisper (and for Google if spike S2 came back positive), and explicitly
absent with an explanation everywhere else. The UI distinguishes *"we have real per-word
confidence"* from *"this provider gives none"* — not by showing zero.

`maxConcurrentRequests: 1`, so no chunking is needed and none is done: faster-whisper takes the
whole normalized file, which also means word timings are continuous and there is no seam de-dup.

Model choice, with measured realtime factors on the reference box (8 vCPU, `int8`):

| Model | Params | RAM | CPU rtf | 1 h audio | GPU fp16 rtf | Multilingual |
|---|---|---|---|---|---|---|
| `large-v3` | 1.55 B | ~4.5 GB | 1–2× | **30–60 min** | 15–30× | yes |
| `large-v3-turbo` | 809 M | ~2.5 GB | 2.5–4× | 15–25 min | 25–50× | yes |
| `distil-large-v3` | 756 M | ~2.5 GB | 3–5× | 12–20 min | 30–60× | **English only** |
| `medium` | 769 M | ~2 GB | 3–6× | 10–20 min | — | yes |

**A correction to the overview.** `00-overview.md` says *"default to `distil-large-v3` and show the
realtime factor in the model picker."* The realtime-factor half is right and stays. The default is
wrong: distil-whisper is distilled on **English** data and is not a multilingual model, so as the
default for a product whose whole reason to exist is 44 non-English languages it would be actively
misleading. The resolution:

```ts
resolveModel(code, { requireWordTimestamps }) {
  if (isEnglish(code)) return 'distil-large-v3';   // genuinely the best speed/quality here
  return settings.fasterWhisperPreferSpeed ? 'large-v3-turbo' : 'large-v3';
}
```

`large-v3` for non-English by default, `large-v3-turbo` behind a "prefer speed" setting, and the
picker explains the swap in one line. The overview's `distil-large-v3` line should get a one-line
amendment. `large-v3` int8 on 8 cores at 1–2× realtime means a one-hour interview takes 30–60
minutes, and that number belongs in the picker, recomputed from the last five runs on this
instance rather than hardcoded.

Weights download on first use into `hf-cache`, which means the first run of a fresh instance
appears to hang for 3 GB. `thibi models pull large-v3` exists so a newsroom can do that
deliberately, and `./thibi doctor` (Phase 15) reports which models are cached.

### 6. Steering: the matrix and `resolveModel`

```ts
// packages/languages/src/choose.ts
export function chooseProvider(
  code: string,
  opts: { requireWordTimestamps: boolean; prefer?: ProviderId[]; allowUnsupported?: boolean }
): { providerId: ProviderId; model: string; tier: Tier; reason: string } | null
```

Precedence: explicit `--provider` → project default → `opts.prefer` → matrix ranking by
`supported && tier`, with Google first for any code where `openai.supported === false` — which is
the 44-language set, i.e. the product. `reason` is always populated and always printed. A silent
provider choice is a support ticket.

```
$ thibi providers list --language my
provider         model               status                                          word ts  word conf
google           chirp_2             verified                                        yes      unknown (S2)
openai           —                   unsupported — code not accepted                 —        —
groq             whisper-large-v3    unsupported — accepted but mangles (2026-07-30) yes      no
faster-whisper   large-v3            experimental — not yet evaluated                yes      YES
```

**Interaction with Phase 5.** These providers exist partly so the harness has comparators, and the
matrix's `evidence: "assumed"` rows *are* the harness's work queue:
`thibi eval asr --providers google,openai,groq,faster-whisper --languages my,yo,ha,ps,km` writes
`language_support` rows and flips `supported` with a number behind it. Two constraints Phase 4 must
honour so that Phase 5 is cheap rather than a rewrite:

1. **Every provider response must be cacheable** by `sha256(provider|model|lang|clipHash|paramsHash)`.
   So each adapter exposes `paramsHash()` and no request may contain a timestamp, nonce or random
   seed. Re-running a sweep after a prompt change must cost nothing for the unchanged arms.
2. **`TranscribeResult.raw` keeps the untouched response body**, and `segments.text_raw` keeps the
   exact provider bytes. Script integrity (`packages/core/src/metrics/script.ts`) is computed on
   `text_raw`, pre-normalizer — a provider that normalizes in place, which is the `lib/queue.ts:126`
   mistake, makes the Groq romanisation invisible to the very metric designed to catch it.

`script.ts` ships in Phase 4, not Phase 5, precisely so the Groq case is documented by a number
from the day the adapter exists.

## Tests

Fixtures in `packages/engine/src/providers/whisper/__fixtures__/`:

| Fixture | Contents |
|---|---|
| `openai-verbose-json-my.json` | Full `verbose_json`, flat `words[]`, realistic `avg_logprob` |
| `openai-words-unattached.json` | A word before the first segment and one straddling a boundary |
| `openai-hallucinated-silence.json` | Trailing `"Thank you."` with `no_speech_prob 0.91` |
| `openai-prompt-echo.json` | First segment beginning with the glossary prompt |
| `groq-my-mangled.json` | **The actual research output** — Myanmar-script non-words, HTTP 200 |
| `groq-my-autodetect-romanised.json` | The romanised autodetect output |
| `groq-429.json` | Rate-limit envelope with `Retry-After` and `x-ratelimit-*` |
| `fw-large-v3-my.json` | Sidecar result with per-word `probability` |

Cases:

- **Word re-attachment** over `openai-words-unattached.json`: the straddling word lands in exactly
  one segment; the orphan is counted, not dropped; `unattached` appears in `usage`.
- `exp(avg_logprob)` is clamped to `[0,1]`; `avg_logprob = -0.0` → `1.0`; a missing field →
  `undefined`, **never** `1`.
- Hallucination guard drops the trailing segment and only that one; a >10% drop rate raises a run
  warning.
- Prompt echo of ≥12 characters is stripped and counted.
- Prompt budget: 400 Burmese glossary terms truncate to ≤200 estimated tokens with the
  highest-`boost` terms retained; truncation is from the back.
- `resolveModel('bn-IN', {requireWordTimestamps:true})` on OpenAI → `null` **with a reason string**;
  `('en-US', …)` → `whisper-1`; `('bn-IN', {requireWordTimestamps:false})` → `gpt-4o-transcribe`.
- `groq.supportsLanguage('my-MM')` → `null` even though the matrix records `accepted: true`. There
  is a **second assertion on the matrix file itself**, so someone regenerating the probe cannot
  quietly flip Burmese back to supported without a red test.
- `scriptIntegrity(groq-my-mangled.json, 'Mymr')` and `(groq-my-autodetect-romanised.json, 'Mymr')`
  are snapshotted, so the romanisation case is a number in CI before the harness exists.
- `chooseProvider('my-MM', …)` returns Google with a reason; with `--provider groq` and no
  `--force-unsupported` it throws a message naming the probe date.
- `paramsHash()` is stable across two identical requests and differs when `prompt` changes — the
  Phase 5 caching contract as an executable test.
- Sidecar `pytest`: word probabilities survive the JSON round-trip to 4 dp;
  `condition_on_previous_text` is `False` in the call; VAD parameters are passed through;
  a `/v1/transcribe` submitted while diarization holds the slot returns 429; a `lost` task after a
  registry reload behaves as in Phase 3.
- Live smoke per provider behind `THIBI_LIVE=1`, never in CI.

## Risks and open questions

1. **The overview's `distil-large-v3` default is wrong for non-English** — distil-whisper is an
   English-only distillation. §5 proposes `large-v3` for non-English with `large-v3-turbo` behind a
   speed setting. This needs a one-line amendment to `00-overview.md`; it is a finding, not a
   preference.
2. **OpenAI's `timestamp_granularities` behaviour and `gpt-4o-*` format support change.** Pin
   current behaviour with recorded fixtures plus a live smoke, and re-probe as part of the Phase 5
   sweep rather than trusting the docs.
3. **The 224-token budget is estimated, not tokenised.** Adding `tiktoken` is the fix, but only
   after Phase 5 measures whether the prompt helps at all — right now "glossary in the prompt
   improves accuracy" is an assumption, and it is cheap to test as an eval arm.
4. **Groq quotas are tight enough that a harness sweep can exhaust them.** Budget guards are
   Phase 5 and the token bucket is Phase 9; Phase 4 only honours `Retry-After` and fails cleanly,
   recording the rate-limit headers so those phases have data.
5. **Marking ~40 unmeasured Groq codes `supported: false, evidence: "assumed"`** will look
   pessimistic and some of them probably do work. That is the intended bias: the product's second
   research finding is that accepting a code proves nothing, and the harness exists to promote them
   one measurement at a time.
6. **Open — is Google's `enableSpeakerDiarization` / `speakerLabel` worth probing** now that Phase 3
   has a `DiarizationSource` interface it could slot into as a zero-cost source? Cheap to test.
   Do it during the Phase 5 probe run, not here.
7. **Open — whether to expose `beam_size` and temperature fallback in the UI.** Default no: they
   are eval knobs. Keep them in `runs.pipeline.params` so the harness can sweep them without a
   schema change.
