# Phase 10 — Auth, users, settings, secrets

## Goal

At the end of this phase a freshly-started instance prints a `/setup` link and a setup token;
the first person with that token becomes admin under a table lock; that admin logs in, pastes a
Google service-account JSON into an API that encrypts it with AES-256-GCM before it touches
disk, clicks Test connection and gets Google's own error text back if it is wrong. Every server
action, route handler and page is gated by `requireUser()`/`requireAdmin()`, and the Next 16
`proxy.ts` does nothing but redirect. This sits at phase 10 because phases 1–9 built an engine
that reads configuration from `ctx.settings` and never from `process.env` — so the only thing
missing is a place for a human to put the values, and a definition of which human. It sits
before the UI phases because every screen in 11–14 assumes a session, a role and a settings API,
and retrofitting authorization onto finished screens is how authorization bugs are made.

This phase designs the **server side and the API surface**. The settings, users and admin
screens are Phase 14.

## Design

### 1. Sessions, not JWT

On a single self-hosted instance, JWT's statelessness buys nothing — there is one process group,
one database, and no cross-service token verification to save a round trip on. What it costs is
concrete: an admin who disables a compromised editor account expects that account dead *now*,
not at the end of a 15-minute access-token window, and the standard fix for that is a
revocation list, which is a session table with extra steps. Newsrooms are exactly the users who
will need instant revocation and will not accept "within fifteen minutes" as the answer.

```sql
CREATE EXTENSION IF NOT EXISTS citext;

CREATE TABLE users (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  username       citext NOT NULL UNIQUE,
  display_name   text NOT NULL,
  email          citext UNIQUE,                 -- nullable; no SMTP in v1, but SSO needs it
  password_hash  text,                          -- nullable: an SSO-only account has none
  role           text NOT NULL DEFAULT 'editor' CHECK (role IN ('admin','editor','viewer')),
  must_change_pw boolean NOT NULL DEFAULT false,
  disabled_at    timestamptz,
  last_login_at  timestamptz,
  created_by     uuid REFERENCES users(id),
  created_at     timestamptz NOT NULL DEFAULT now(),
  updated_at     timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE sessions (
  id           bytea PRIMARY KEY,               -- sha256(token). The token is never stored.
  user_id      uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  expires_at   timestamptz NOT NULL,
  created_at   timestamptz NOT NULL DEFAULT now(),
  last_seen_at timestamptz NOT NULL DEFAULT now(),
  ip           inet,
  user_agent   text
);
CREATE INDEX sessions_user_idx    ON sessions (user_id);
CREATE INDEX sessions_expiry_idx  ON sessions (expires_at);
```

**Shaped so `accounts` bolts on later.** `password_hash` and `email` are nullable and `username`
is the identity; adding SSO is then one new table and zero changes to `users`:

```sql
-- NOT built in v1. Written down so v1 does not preclude it.
```

**The token.**

```ts
const COOKIE = process.env.PUBLIC_URL?.startsWith('https:') ? '__Host-thibi_session' : 'thibi_session';
const TTL_MS = 30 * 24 * 3600_000;      // 30 days
const RENEW_WINDOW_MS = 15 * 24 * 3600_000;

export async function createSession(userId: string, req: RequestMeta) {
  const token = base64url(randomBytes(32));                 // 256 bits; the only copy is the cookie
  const id = createHash('sha256').update(token).digest();   // bytea, 32 bytes
  await db.insert(sessions).values({
    id, userId, expiresAt: new Date(Date.now() + TTL_MS), ip: req.ip, userAgent: req.ua,
  });
  return { token, cookie: {
    name: COOKIE, value: token, httpOnly: true, sameSite: 'lax' as const,
    secure: COOKIE.startsWith('__Host-'), path: '/', maxAge: TTL_MS / 1000,
  }};
}

export async function readSession(token: string | undefined) {
  if (!token) return null;
  const id = createHash('sha256').update(token).digest();
  const row = await db.select(...).from(sessions)
    .innerJoin(users, eq(users.id, sessions.userId))
    .where(and(eq(sessions.id, id), gt(sessions.expiresAt, new Date())))
    .limit(1);
  if (!row.length || row[0].users.disabledAt) return null;

  // Sliding renewal, but only ONE write per session per 15 days. A write on every
  // request turns a read-only page load into a write transaction and, on a busy editor,
  // into row-lock contention on a single hot row.
  const s = row[0].sessions;
  if (+s.expiresAt - Date.now() < RENEW_WINDOW_MS) {
    await db.update(sessions)
      .set({ expiresAt: new Date(Date.now() + TTL_MS), lastSeenAt: new Date() })
      .where(eq(sessions.id, id));
  }
  return row[0].users;
}
```

Hashing the token means a leaked database backup contains no usable sessions — the same threat
the secrets design targets, closed the same way. Lookup is by primary key on the hash, so there
is no performance cost.

`__Host-` requires `Secure`, which breaks a plain-HTTP LAN install; the cookie name is chosen
from `PUBLIC_URL` at build/boot and logged once at startup so the choice is visible.

**Passwords: `@node-rs/argon2`.** Chosen over `argon2` (node-gyp) and `bcrypt` for one operational
reason: prebuilt binaries for linux-x64-gnu, linux-arm64-gnu and darwin mean **no compiler in
the Docker image**. Adding `build-essential` and `python3` to a production image to hash a
password is 300 MB and a supply-chain surface, and it breaks on Alpine in a way that a
non-sysadmin cannot debug.

```ts
import { hash, verify, Algorithm } from '@node-rs/argon2';
const PARAMS = { algorithm: Algorithm.Argon2id, memoryCost: 19456, timeCost: 2, parallelism: 1 };
// OWASP 2024 minimum. 19 MiB × concurrent logins is real memory on a 4 GB box —
// which is a second, independent reason the login rate limiter in §3 exists.

const DUMMY = await hash('x'.repeat(32), PARAMS);   // computed once at boot
export async function verifyPassword(stored: string | null, given: string) {
  // Always do the work, even for an unknown username: otherwise response timing
  // enumerates valid accounts, and a newsroom's staff list is not public information.
  return verify(stored ?? DUMMY, given, PARAMS) && stored !== null;
}
```

**Rejected, explicitly.** *Lucia* is deprecated — its author now ships it as a learning resource,
and adopting a library whose maintainer has told you to stop is a liability in software a
newsroom will run for years. *Auth.js* configured for credentials-only is more configuration
than the ~200 lines above: you write the authorize callback, the adapter, the session strategy
and the callbacks, and you inherit a JWT-first design you then argue with. *better-auth* is the
escape hatch and the one to reach for if SSO is ever required — it has real session support and
an OIDC plugin, and the `users` shape above is compatible with its expectations. That is a
migration, not a rewrite, precisely because we own the table.

### 2. Next.js 16 integration

**`proxy.ts`, not `middleware.ts`.** Next 16 renames the file and the export; a `middleware.ts`
in a Next 16 app is silently ignored, which fails *open* if the file is treated as a security
control. It is not treated as one here.

```ts
// apps/web/proxy.ts
//
// THIS IS NOT AN AUTHORIZATION BOUNDARY.
// It is a redirect optimisation so an unauthenticated user hits /login without a
// round trip through a server component. It checks for the PRESENCE of a cookie and
// never validates it. CVE-2025-29927 was a middleware-authorization bypass via a
// spoofable internal header; the structural lesson is that authorization must live
// where the data is read, not in a request-path filter that something upstream can skip.
import { NextResponse, type NextRequest } from 'next/server';

export const config = {
  matcher: ['/((?!_next/static|_next/image|favicon.ico|api/health|setup).*)'],
};

export default function proxy(req: NextRequest) {
  const hasCookie = req.cookies.has(SESSION_COOKIE);
  const isAuthPage = req.nextUrl.pathname.startsWith('/login');
  if (!hasCookie && !isAuthPage) {
    const url = req.nextUrl.clone();
    url.pathname = '/login';
    url.searchParams.set('next', req.nextUrl.pathname + req.nextUrl.search);
    return NextResponse.redirect(url);
  }
  if (hasCookie && isAuthPage) return NextResponse.redirect(new URL('/', req.url));
  return NextResponse.next();
}
```

**The real gate.**

```ts
// apps/web/src/auth/current-user.ts
import { cache } from 'react';

// cache() dedupes per request: a page with a header, a sidebar and four server
// components does ONE session lookup, not six. This is why it is cache() and not a
// module-level memo — module scope would leak one user's session to another request.
export const getCurrentUser = cache(async (): Promise<AuthUser | null> => {
  const token = (await cookies()).get(SESSION_COOKIE)?.value;
  return readSession(token);
});

export async function requireUser(): Promise<AuthUser> {
  const u = await getCurrentUser();
  if (!u) redirect('/login');
  if (u.mustChangePw && !isChangePasswordRoute()) redirect('/account/password');
  return u;
}

export async function requireAdmin(): Promise<AuthUser> {
  const u = await requireUser();
  if (u.role !== 'admin') notFound();   // 404, not 403: do not confirm the route exists
  return u;
}
```

**Server Actions are publicly-callable POST endpoints.** Next compiles every exported async
function in a `'use server'` file into an RPC endpoint reachable by anyone who can guess or scrape
its action id. An action that reads `getCurrentUser()` but forgets to check `role` is an
authorization bug; an action that checks nothing is a remote-code-path for the internet.

```ts
// apps/web/src/auth/action.ts
type ActionResult<O> = { ok: true; data: O } | { ok: false; error: string; field?: string };

export function action<S extends z.ZodTypeAny, O>(opts: {
  input: S;
  role?: Role | Role[];                       // omit = any authenticated user
  audit?: { action: string; entity: string };
  rateLimit?: { key: string; perMinute: number };
  handler: (a: { user: AuthUser; input: z.infer<S>; ip: string }) => Promise<O>;
}) {
  return async function boundAction(raw: unknown): Promise<ActionResult<O>> {
    const user = await getCurrentUser();
    if (!user) return { ok: false, error: 'Not signed in' };
    if (opts.role && !roleAllows(user.role, opts.role)) return { ok: false, error: 'Not permitted' };

    const ip = await clientIp();
    if (opts.rateLimit && !(await allow(`${opts.rateLimit.key}:${user.id}`, opts.rateLimit.perMinute)))
      return { ok: false, error: 'Too many requests' };

    const parsed = opts.input.safeParse(raw);
    if (!parsed.success) {
      const i = parsed.error.issues[0];
      return { ok: false, error: i.message, field: i.path.join('.') };
    }

    try {
      const data = await opts.handler({ user, input: parsed.data, ip });
      if (opts.audit) await audit({ actor: user, ip, ...opts.audit, after: redactForAudit(data) });
      return { ok: true, data };
    } catch (err) {
      logger.error({ err, action: opts.audit?.action }, 'action failed');
      return { ok: false, error: userFacing(err) };   // never the raw message
    }
  };
}
```

### 3. First-run bootstrap

The failure mode being prevented is specific. `./thibi up -d` on a VPS with a public IP starts
serving before the admin has finished reading the terminal output. If `/setup` were reachable to
anyone while zero users exist, then whoever port-scans that IP first becomes the administrator
of a machine holding a newsroom's source recordings. Scanners find a new host on a common cloud
range in minutes. "Zero users exist" is not an authentication factor.

So `/setup` requires **both** conditions:

```ts
export const bootstrapAdmin = async (raw: unknown) => {
  const input = SetupSchema.parse(raw);   // username, displayName, password (min 12), token

  // 1. Setup token — constant-time compare, and the token is single-purpose.
  const expected = await readSetupToken();      // data/setup-token, 0600, written by `thibi init`
  const given = Buffer.from(input.token);
  if (!expected || given.length !== expected.length || !timingSafeEqual(given, expected)) {
    await sleep(500 + Math.random() * 500);
    return { ok: false as const, error: 'Invalid setup token' };
  }

  // 2. Zero users, under a lock that serialises concurrent setup attempts.
  return db.transaction(async (tx) => {
    // EXCLUSIVE (not ACCESS EXCLUSIVE) blocks every writer and every other LOCK, while
    // still permitting plain reads. Two simultaneous POSTs cannot both see count = 0.
    await tx.execute(sql`LOCK TABLE users IN EXCLUSIVE MODE`);
    const [{ n }] = await tx.select({ n: count() }).from(users);
    if (n > 0) return { ok: false as const, error: 'Setup has already been completed' };

    const user = await tx.insert(users).values({
      username: input.username, displayName: input.displayName,
      passwordHash: await hash(input.password, PARAMS),
      role: 'admin', mustChangePw: false,
    }).returning();

    await auditTx(tx, { actorId: user.id, action: 'setup.bootstrap', entity: 'user', entityId: user.id });
    return { ok: true as const, userId: user.id };
  });
};
```

After success, `consumeSetupToken()` deletes the token file. `GET /setup` returns **404** once
any user exists — not 403, which confirms the endpoint is real and tells a scanner the instance
is initialised.

**No SMTP on a self-hosted box.** There is no mail server, and requiring one would put an SPF/
DKIM problem between a newsroom and its transcription tool. So the account lifecycle is:

| Flow | Mechanism |
|---|---|
| Admin creates a user | Server generates a 16-character password from an unambiguous alphabet (no `0/O/1/l/I`), stores the argon2id hash, sets `must_change_pw = true`, and returns the plaintext **once** in the creation response. It is never retrievable again — a second GET returns the user row without it. |
| User's first login | `requireUser()` redirects to `/account/password` until `must_change_pw` clears. Changing it revokes every other session for that user. |
| Forgotten password | `thibi admin reset-password <username>` — break-glass, on the box, prints a new one-time password and sets `must_change_pw`. Also `--revoke-sessions`. |
| Compromised account | `thibi admin disable <username>` sets `disabled_at`; `readSession` rejects immediately. Instant, which is the whole argument in §1. |

The one-time-password-shown-once flow is deliberately a little awkward — an admin has to hand it
over out of band. That is honest for a tool with no mailer, and it is much better than a
"reset link" that requires configuring SMTP before anyone can log in.

**Rate limiting** — per username *and* per IP, because either alone is trivially defeated:
per-IP only is beaten by a botnet, per-username only lets an attacker spray one password across
every account.

```sql
CREATE TABLE auth_attempts (
  bucket        text PRIMARY KEY,        -- 'u:alice' | 'ip:203.0.113.7'
  fails         integer NOT NULL DEFAULT 0,
  window_start  timestamptz NOT NULL DEFAULT now(),
  locked_until  timestamptz
);
```

| Bucket | Threshold | Lock |
|---|---|---|
| `u:<username>` | 5 failures in 15 min | 15 min |
| `ip:<addr>` | 20 failures in 15 min | 15 min |
| `setup` | 5 failures ever | 60 min, and log at `warn` |

A locked bucket returns the same generic "Incorrect username or password" as a wrong password —
telling an attacker they have found a real username and locked it is free reconnaissance. Locks
clear on success. A successful login resets the username bucket only.

```ts
// apps/web/src/auth/client-ip.ts
// X-Forwarded-For is attacker-controlled unless something you trust rewrites it.
// With TRUSTED_PROXY unset, per-IP limiting on a spoofed header is worse than none:
// it lets an attacker lock OTHER people out by forging their address.
export async function clientIp(): Promise<string> {
  const h = await headers();
  if (env.TRUSTED_PROXY) {
    const xff = h.get('x-forwarded-for');
    if (xff) return xff.split(',').at(-1)!.trim();   // rightmost = added by our own proxy
  }
  return h.get('x-real-ip') ?? '0.0.0.0';
}
```

`./thibi init` sets `TRUSTED_PROXY=1` because Caddy is always in front in the shipped Compose
file; a bare `next start` deployment must not.

### 4. Roles

Confirmed: **admin** and **editor**.

| Capability | admin | editor | *viewer (proposed)* |
|---|---|---|---|
| View jobs, transcripts, play audio | ✓ | ✓ | ✓ |
| Export (SRT/VTT/TXT/JSON/docx) | ✓ | ✓ | ✓ |
| Edit segments, speakers, glossaries | ✓ | ✓ | ✗ |
| Upload media, **start runs, run editorial passes** | ✓ | ✓ | ✗ |
| Cancel/retry runs | ✓ | ✓ (own project) | ✗ |
| Settings, provider keys, model profiles | ✓ | ✗ | ✗ |
| Users, retention, `/admin/*`, spend | ✓ | ✗ | ✗ |

**Viewer is a decision, not an assumption.** The argument for it is money: *starting a run is
the only action in this product that spends money*, and a newsroom will want to give a
fact-checker, a freelancer or a lawyer read access to a transcript without giving them the
ability to run a $9 batch job or a translation pass across four languages. The argument against
is that three roles is where per-object permissions start being asked for ("viewer on this
project only"), and that is a much larger design.

Recommendation: **ship the `role` CHECK constraint with `'viewer'` allowed from day one**, and
implement the role only if the first partner newsroom asks. The column shape is the expensive
part of the decision; the enforcement is a few `roleAllows` calls. Do not build the UI for it in
phase 14 unless it has been confirmed. Flag this for the user rather than silently choosing.

Implementation is a total order, `admin > editor > viewer`, plus a small capability map — not an
ACL. If per-project permissions ever arrive they need a `project_members` table, and that is a
different phase.

### 5. Secrets

AES-256-GCM, key from `APP_SECRET_KEY`, ciphertext in Postgres.

```sql
CREATE TABLE settings (
  key           text PRIMARY KEY,
  value         jsonb,                    -- non-secret values, structured
  secret_ct     bytea,                    -- ciphertext        } exactly one of
  secret_nonce  bytea,                    -- 12-byte nonce     } (value) or
  secret_tag    bytea,                    -- 16-byte GCM tag   } (ct,nonce,tag) is set
  is_secret     boolean NOT NULL DEFAULT false,
  hint          text,                     -- 'sk-ant-…4f2a' — safe to render
  key_version   integer NOT NULL DEFAULT 1,
  updated_by    uuid REFERENCES users(id),
  updated_at    timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT settings_shape CHECK (
    (is_secret AND secret_ct IS NOT NULL AND secret_nonce IS NOT NULL AND secret_tag IS NOT NULL AND value IS NULL)
    OR (NOT is_secret AND secret_ct IS NULL)
  )
);
```

```ts
// packages/engine/src/secrets/crypto.ts
import { createCipheriv, createDecipheriv, hkdfSync, randomBytes, timingSafeEqual } from 'node:crypto';

/**
 * APP_SECRET_KEY is 32 random bytes, base64. HKDF gives us a domain-separated
 * sub-key so the same master can later derive independent keys for other purposes
 * (backup encryption, signed URLs) without any of them being the same bytes.
 */
function deriveKey(masterB64: string, purpose = 'settings-v1'): Buffer {
  const master = Buffer.from(masterB64, 'base64');
  if (master.length !== 32) throw new Error('APP_SECRET_KEY must be 32 bytes, base64-encoded');
  return Buffer.from(hkdfSync('sha256', master, Buffer.from('thibi'), Buffer.from(purpose), 32));
}

export interface Sealed { ct: Buffer; nonce: Buffer; tag: Buffer }

/**
 * AAD binds the ciphertext to the setting KEY NAME.
 *
 * Without it, every ciphertext in the table is interchangeable. Anyone with UPDATE on
 * `settings` — a compromised web process, a misconfigured DB grant, an SQL injection in
 * some future admin filter — could copy `google_sa_json`'s ciphertext into
 * `smtp_password`, then read the "SMTP password" back through a UI that happily
 * decrypts and displays it. Authentication of the ciphertext alone does not stop that;
 * the tag is still valid, because the bytes were not altered, only relocated.
 * With AAD, a moved row fails to open. This costs one line and closes a real path.
 */
function aad(name: string): Buffer {
  return Buffer.from(`thibi:settings:v1:${name}`, 'utf8');
}

export function seal(key: Buffer, name: string, plaintext: string): Sealed {
  const nonce = randomBytes(12);                      // GCM: 96-bit, random, never reused
  const c = createCipheriv('aes-256-gcm', key, nonce);
  c.setAAD(aad(name));
  const ct = Buffer.concat([c.update(plaintext, 'utf8'), c.final()]);
  return { ct, nonce, tag: c.getAuthTag() };
}

export function open(key: Buffer, name: string, s: Sealed): Secret {
  const d = createDecipheriv('aes-256-gcm', key, s.nonce);
  d.setAAD(aad(name));
  d.setAuthTag(s.tag);
  try {
    return new Secret(Buffer.concat([d.update(s.ct), d.final()]).toString('utf8'));
  } catch {
    // Do not echo the key name in a way that ends up in a user-facing string —
    // but DO make the operator's diagnosis easy, because there are only three causes.
    throw new SecretDecryptError(
      `Could not decrypt setting "${name}". Either APP_SECRET_KEY has changed since it ` +
      `was saved, the value was moved between settings rows, or the row is corrupt. ` +
      `Run \`thibi secrets check\` to see which settings are affected.`);
  }
}
```

**The hint.** `hint` is computed at save time and is the only part of a secret ever rendered:
first 7 characters, ellipsis, last 4, for values ≥ 16 characters; `'••••'` otherwise. For
service-account JSON the hint is the `client_email` instead, which is far more useful than a
prefix of a PEM block and is not itself a secret.

**Threat model — this paragraph goes verbatim into `docs/security.md` and the README:**

> **What encrypted settings protect you from.** Provider credentials — your Google
> service-account key, your Anthropic and OpenAI keys — are stored in the database encrypted
> with AES-256-GCM under a key held in `APP_SECRET_KEY`, which lives in your `.env` file and is
> never written to the database. This protects you if a database backup leaks. That is the
> realistic failure: `pg_dump` output gets copied to a laptop, attached to a support ticket, or
> synced to Dropbox, and a plaintext `settings` table in any of those places is a set of live
> API keys someone can bill against. An encrypted one is not.
>
> **What it does not protect you from.** It does not protect you from someone with root on the
> host, or from anyone who can read `.env` — they have the key and the database and can decrypt
> everything. It is not a hardware security module and it is not key management. Back up
> `APP_SECRET_KEY` **separately from your database backups**, keep it out of version control,
> and treat host access as equivalent to full credential access.

`thibi backup` warns loudly that `APP_SECRET_KEY` is not in the backup; `thibi restore` probes
decryption immediately, so a lost key is discovered during a drill rather than during an
incident.

**Rotation.**

```bash
APP_SECRET_KEY_OLD=<old base64>  APP_SECRET_KEY=<new base64>  thibi secrets rotate
```

```ts
export async function rotateSecrets(db: Db, oldB64: string, newB64: string) {
  const oldKey = deriveKey(oldB64), newKey = deriveKey(newB64);
  await db.transaction(async (tx) => {
    // Serialise against concurrent settings writes for the whole rotation.
    await tx.execute(sql`LOCK TABLE settings IN SHARE ROW EXCLUSIVE MODE`);
    const rows = await tx.select().from(settings).where(eq(settings.isSecret, true));
    for (const r of rows) {
      // Decrypt with the OLD key under the SAME name, re-seal with the NEW key under
      // the same name: the AAD is unchanged, so rotation cannot silently re-bind a value.
      const plain = open(oldKey, r.key, { ct: r.secretCt!, nonce: r.secretNonce!, tag: r.secretTag! });
      const sealed = seal(newKey, r.key, plain.expose());
      await tx.update(settings)
        .set({ secretCt: sealed.ct, secretNonce: sealed.nonce, secretTag: sealed.tag,
               keyVersion: r.keyVersion + 1 })
        .where(eq(settings.key, r.key));
    }
    return rows.length;
  });
  // All-or-nothing. A partial rotation leaves half the table unreadable by either key,
  // which is the worst possible outcome and the reason this is one transaction.
}
```

`thibi secrets check` opens every secret with the current key and reports pass/fail per key
without printing values — the drill command, and the thing to run after a restore.

`thibi secrets list` prints key, `is_secret`, `hint`, `updated_at`, `updated_by`. Never values.
There is no command that prints a secret. If an operator needs the key back they have it in
their own password manager; a tool that can exfiltrate every credential with one command is a
tool an attacker uses first.

**Not Vault.** That is the line, and it is worth stating why in one sentence: this product's
deployment target is a newsroom running `docker compose up` on one VPS, and adding a service
that requires unsealing after every restart converts "the transcription tool is down" into "the
transcription tool is down and nobody here knows what unsealing is". The same reasoning rules
out SOPS-with-age as a *required* path, though nothing stops an operator from keeping their
`.env` in SOPS.

```ts
export async function validateStagingBucket(bucket: string, ctx: SettingsCtx): Promise<ValidationResult> {
  const region = (await ctx.get('google_region')).value ?? 'asia-southeast1';
  const token = await mintToken(await ctx.getSecret('google_sa_json'));
  const res = await fetch(
    `https://storage.googleapis.com/storage/v1/b/${encodeURIComponent(bucket)}?fields=location,locationType,lifecycle`,
    { headers: { Authorization: `Bearer ${token}` } });

  if (res.status === 404) return { ok: false, message: `Bucket "${bucket}" does not exist, or this service account cannot see it.` };
  if (res.status === 403) return { ok: false, message: `This service account cannot read bucket "${bucket}". It needs roles/storage.objectAdmin.` };
  if (!res.ok) return { ok: false, message: await googleErrorText(res) };

  const b = await res.json() as { location: string; locationType: string; lifecycle?: { rule: unknown[] } };
  if (!locationCoversRegion(b.location, b.locationType, region)) {
    return { ok: false, message:
      `Bucket "${bucket}" is in ${b.location} but the recognizer region is ${region}. ` +
      `batchRecognize requires them to match. Create the bucket in ${region}, or change the region.` };
  }
  if (!hasOneDayLifecycle(b.lifecycle)) {
    return { ok: true, warning:
      `No 1-day deletion lifecycle rule on "${bucket}". Staged audio would accumulate and be billed. ` +
      `Run:  gsutil lifecycle set infra/gcs-staging-lifecycle.json gs://${bucket}` };
  }
  return { ok: true };
}
```

`locationCoversRegion` handles the multi-region case: a bucket in `ASIA` covers

covers either. Getting this wrong in the strict direction is worse than in the permissive one —
a false rejection blocks a working configuration — so a location we cannot classify produces a
**warning**, not an error, with the exact strings printed so an operator can judge.

### 9. Secret hygiene

Four mechanisms, because one is never enough.

**(a) The `Secret` branded class.** A plaintext credential is never a bare `string` anywhere in
the codebase. Every accidental path out — template literal, `console.log`, `JSON.stringify`,
`util.inspect`, a pino serializer, an error message that interpolates a config object — is
closed by construction rather than by remembering.

```ts
// packages/engine/src/secrets/secret.ts
export class Secret {
  readonly #value: string;
  constructor(value: string) { this.#value = value; }

  /** The single, greppable way to get the plaintext. `rg '\.expose\(\)'` audits every use. */
  expose(): string { return this.#value; }

  toString(): string { return '[redacted]'; }
  toJSON(): string { return '[redacted]'; }
  [Symbol.toPrimitive](): string { return '[redacted]'; }
  [Symbol.for('nodejs.util.inspect.custom')](): string { return '[redacted]'; }
  get [Symbol.toStringTag]() { return 'Secret'; }
}
```

A `#private` field, not `private` — TypeScript's `private` is erased and
`JSON.stringify(secret)` would emit it. The class is in `packages/engine` and re-exported; a
lint rule bans `.expose()` outside `packages/engine/src/providers/**` and
`packages/engine/src/settings/probe.ts`. `ctx.settings.getSecret()` returns `Secret`; there is
no overload returning `string`.

**(b) pino redaction.**

```ts
export const REDACT_PATHS = [
  'req.headers.authorization', 'req.headers.cookie', 'req.headers["x-api-key"]',
  'res.headers["set-cookie"]',
```

Redaction is the backstop, not the design. It only catches the paths you thought of, which is
exactly why (a) exists.

**(c) Never write secrets to `run_steps.input`.** Step payloads carry **key names**; the worker
resolves them from `ctx.settings` at execution time. Three reasons, all real: `/admin/queue`
renders `input` verbatim; `input` persists in the database for the run's whole life and into
every backup; and a rotated key would leave stale credentials in step rows forever.


```ts
it('no step input contains anything that looks like a credential', async () => {
  const rows = await db.select({ input: runSteps.input }).from(runSteps);
  const patterns = [/sk-[A-Za-z0-9]{20,}/, /BEGIN [A-Z ]*PRIVATE KEY/, /"private_key"/,
                    /gsk_[A-Za-z0-9]{20,}/, /sk-or-v1-/, /[A-Za-z0-9+/]{60,}={0,2}/];

    for (const p of patterns) expect(s).not.toMatch(p);

});
```

The last pattern (any base64 run of 60+ characters) is deliberately broad and will occasionally
false-positive on a legitimate hash. That is the correct trade: an annoying test failure costs
minutes; a service-account key in a backup costs a project.

**(d) Scrub provider error bodies before storage.** Google echoes fragments of the request in
`error.details` on a 400 — including, for a malformed `inlinePhraseSet` or a bad recognizer
config, chunks of what you sent. `run_steps.error` is stored, backed up, and rendered on
`/admin/queue`.

```ts
const SECRET_SHAPES: Array<[RegExp, string]> = [
  [/\bsk-ant-[A-Za-z0-9_-]{10,}/g,      'sk-ant-[redacted]'],
  [/\bsk-or-v1-[A-Za-z0-9_-]{10,}/g,    'sk-or-v1-[redacted]'],
  [/\bsk-[A-Za-z0-9]{20,}/g,            'sk-[redacted]'],
  [/\bgsk_[A-Za-z0-9]{20,}/g,           'gsk_[redacted]'],
  [/\bya29\.[A-Za-z0-9._-]{20,}/g,      'ya29.[redacted]'],          // Google access token
  [/-----BEGIN[\s\S]*?END [A-Z ]*-----/g, '[redacted private key]'],
  [/"private_key"\s*:\s*"[^"]*"/g,      '"private_key":"[redacted]"'],
  [/\bBearer\s+[A-Za-z0-9._~+/-]{20,}/g,'Bearer [redacted]'],
  [/eyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}/g, '[redacted jwt]'],
];

export function scrubProviderError(input: unknown): { code?: string; message: string; status?: number; at: string } {
  let msg = typeof input === 'string' ? input
          : input instanceof Error ? input.message
          : JSON.stringify(input);
  for (const [re, sub] of SECRET_SHAPES) msg = msg.replace(re, sub);
  return {
    code: (input as { code?: string })?.code,
    status: (input as { status?: number })?.status,
    // 4 KB: enough for a real Google error with details, small enough that a run with
    // 180 failed chunks does not put a megabyte of duplicated stack traces in the backup.
    message: msg.slice(0, 4096),
    at: new Date().toISOString(),
  };
}
```

Scrubbing happens at the **storage** boundary (`onStepError` in phase 9 §5, and
`providerErrorText` in §7 above), not at the logging boundary, so a secret cannot reach the
database even if logging is disabled.

## Risks and open questions

1. **`APP_SECRET_KEY` loss is unrecoverable, and the person most likely to lose it is the person
   least likely to read the docs.** Mitigations, all of them shipped here: `thibi init` prints
   the key once and tells you to store it in a password manager; `thibi backup` refuses to run
   silently without emitting the warning; `thibi restore` probes decryption immediately;
   `/admin/system` shows a red banner if any secret fails to decrypt. Residual risk is real —
   consider, in phase 15, writing the key to a second file (`APP_SECRET_KEY.backup`, mode 0400)
   with a comment explaining what it is, on the grounds that a key on the same disk is still
   better than no key when the disk is what survived.
2. **Open: viewer role.** §4. Needs a decision from the user, not an assumption. Ship the CHECK
   constraint permitting it; ship the behaviour only on confirmation.
3. **argon2id memory under concurrent logins.** 19 MiB × 20 simultaneous attempts is 380 MB of
   transient allocation on a box speced at 4 GB. The rate limiter caps this, but an admin who
   raises `memoryCost` following a blog post could make login an OOM vector. Clamp `memoryCost`
   to 64 MiB in code and log the effective parameters at boot.
4. **The setup token is a file on disk.** Anyone who can read `infra/data/setup-token` before
   first login can become admin. That is the same person who can read `.env`, so it adds no new
   exposure — but it means the token must be deleted on success (it is) and must not be logged
   (assert in a test).
5. **Next 16 `proxy.ts` API is young.** If the matcher semantics change, the failure mode is
   over- or under-redirecting, never an authorization bypass, because the proxy is not the gate.
   That is the entire reason for the design and worth restating in the file's header comment.
6. **Open: session cookie on a plain-HTTP LAN install.** Falling back from `__Host-` to a plain
   cookie name is correct for usability and worse for security (no `Secure`, so a network
   attacker can steal it). Recommendation: log a `warn` at every boot when `PUBLIC_URL` is
   `http:` and non-localhost, and say so in the install docs. Do not silently downgrade without
   telling anyone.
7. **Rate limiting is per-instance and in Postgres.** Correct for one instance per newsroom;
   it would need rethinking behind a load balancer. Not a v1 concern, but the `auth_attempts`
   table is already shared state, so it would actually survive the change.
8. **Provider probes cost a network round trip on a settings page load** if the UI decides to
   run them automatically. It should not: probes are explicit button presses (phase 14). Note it
   here so phase 14 does not "helpfully" auto-test on mount and turn a page load into ten
   outbound requests.
